# 개인정보

## 어디에 두나 (027 규약)

| | |
|---|---|
| **`leads` 컬럼** | 이름 · 전화 · 이메일 · 직함 |
| **`customer_meta` (jsonb)** | 업종 · 규모 · 도입 대상 · 도입 시기 · 보안 스택 — **개인정보 아님** |

`leads` 는 동의 이력(`consent_at`·`consent_version`·`consent_purpose`·`consent_retention`)을
갖는 표다. **개인정보는 동의와 같은 자리에 있어야** 보유기간 만료 때 함께 지운다.
`customer_meta` 는 `deals` 로 흘러가 영업이 자유롭게 고치는 자유형 필드라, 거기 두면
어디까지 퍼졌는지 추적할 수 없다.

## 수집 항목을 늘리면 셋을 같이 고친다

1. `readiness.html` 의 「수집 항목」 문구
2. `routes/hub.js` 의 `PRIVACY_NOTICE.version`
3. 검사 (`test/lead-contact.test.js` 의 「항목을 늘렸으면 고지와 동의 버전도 같이 올린다」)

항목만 늘리고 고지를 안 고치면 **동의 범위를 벗어난다.** UI 문제가 아니라 법적 문제다.
버전을 안 올리면 옛 동의와 새 동의로 받은 건이 섞여 "이 사람은 무엇에 동의했나"를
되찾을 수 없다. 지난 버전으로 되돌아가지 못하게 검사가 막는다.

`PRIVACY_NOTICE` 는 **화면 고지와 한 글자도 어긋나면 안 된다.**

## 딜로 복사하지 않는다

포탈 원본은 허브에서 **읽기 전용**으로만 보여준다(`portalContactMarkup()`). 편집 가능한
칸에 리드 이메일을 미리 채워 놓았더니, 영업이 한 글자만 건드려도 개인정보가
`customer_meta` 로 복사됐다.

출처가 다른 값은 컬럼도 다르다.

| | |
|---|---|
| `leads.contact_title` | 고객이 폼에서 직접 낸 것 |
| `deals.customer_contact_title` | 영업이 미팅에서 확인한 것 |

섞으면 "고객이 그렇게 말했다"와 "영업이 그렇게 안다"를 구분할 수 없다.

## 목록 응답에 PII 를 싣지 않는다

**`GET /deals` 에는 owner 게이트가 없다** — 승인된 전 직원이 본다. 그래서 목록은
컬럼을 명시 열거하고 `customer_meta` 도 몇 키만 뽑는다. 상세(`GET /deals/:id`)만
담당자·admin·미배정 딜로 제한된다.

새 필드를 추가할 때 **목록에 실을 이유가 없으면 싣지 않는다.**

## 나가는 곳도 본다

- **Slack 알림에 전화번호를 넣지 않는다** — Slack 채널은 보존기간 관리 밖이다
- **공개 결과 링크**(`/r/:token`)에 담당자 이름·전화·이메일을 싣지 않는다. 회사명과
  진단 결과까지다
- 문서로 내보낼 때도 같다 — 고객용 키트는 연락처를 안 부른다

## 검증 형식을 조이지 않는다

전화번호는 모양을 강제하지 않고 자릿수(8~15)로만 본다. 패턴을 잡으면
`02-1234-5678 (내선 301)` 같은 정상 번호를 거절해 **리드를 통째로 잃는다.**

## 행동 기록

열람·클릭 같은 기록은 **요약만** 남긴다(처음·마지막·횟수). IP·User-Agent·이벤트별 행을
남기면 개인 행동 추적이 된다 — **고지에 쓸 수 없는 것을 저장하지 않는다.**
048 이 선례이고, 검사가 이벤트 표 생성과 `ip_address`/`user_agent` 컬럼을 막는다.
