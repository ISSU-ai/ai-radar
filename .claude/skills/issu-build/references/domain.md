# 판정과 오퍼링 구조

## 판정은 두 층이다 — 키가 안 겹친다

| | 무엇을 판정하나 | 키 |
|---|---|---|
| **ISV 솔루션** | 10 평가영역 | `A01`~`A10` |
| **패키지·오퍼링** | 42문항 6축 | `S` `P` `D` `T` `B` `G` |

두 층을 섞지 않는다. ISV 는 「이 제품을 넣을 만한가」, 패키지는 「이 조직이 어느
축에서 약한가」를 본다.

6축 — `S` 전략·리더십 / `P` 인재·조직문화 / `D` 데이터 기반 / `T` 시스템·인프라 /
`B` 업무 적용·성과 / `G` 신뢰·안전 관리. 축마다 7문항 = 42.

## 모르면 판정하지 않는다

판정 입력이 비었을 때 기본값·평균·추정으로 채우지 않는다. **확인 경로로 넘긴다** —
이미 그 경로가 있다: `kind:'manual'` 전제 → STEP03 후보 옆 체크박스
(`prereq_confirmations`, 후보별로 따로 남는다).

때우면 **낙관적으로 틀린다.** 막혔어야 할 후보가 추천에 올라오고 화면엔 티가 안 난다.
빈칸은 영업이 보고 채우지만 **틀린 값은 그냥 통과한다.**

실제로 이렇게 처리했다.

| 상황 | 안 한 것 | 한 것 |
|---|---|---|
| 전제가 지목한 평가영역을 모를 때 | 다른 영역 평균으로 때우기 | 확인 필요로 올린다 |
| 21→10 대응이 없는 전제 | 그냥 버리기 | `kind:'manual'` 로 살린다 |
| 42문항에 근거가 없는 ISV 번들 | 비슷한 문항 갖다 붙이기 | `readiness_signal` 을 비운다 |
| 고객이 보안 제품명을 모를 때 | 후보에서 제외 | `existing`·`managed` 는 판정 안 함 |
| M/D 단가가 없을 때 | 그럴듯한 숫자 | `price_is_placeholder` → 「별도협의」 |
| 개발조직 유무를 알 수 없을 때 | `T1`(MLOps)로 유추 | `E-2` 는 추론하지 않는다 |

한 번 어겼다가 고쳤다 — 엔진이 문항 점수가 없으면 **카테고리 평균**으로 판정했다.
bridge 로 일부만 채워지면서 「접근권한이 3점 이상인가」를 다른 두 문항 평균으로
판정하는 꼴이 됐다. 폴백을 끊고 확인으로 돌렸다.

## 표시도 원칙에 포함된다

자동으로 채워진 값과 사람이 넣은 값은 **화면에서 구분한다.** 근거가 고객 응답인지 영업
추정인지 모르면 그 값도 못 쓴다.

원본을 남기는 컬럼이 그래서 있다 — `readiness_customer_scores`(032) ·
`customer_meta_original`(049). **둘 다 접수 때 한 번 쓰고 다시 안 쓴다.**
`EDITABLE_DEAL_FIELDS` 밖이라 PATCH 로도 못 고친다.

## 패키지는 두 어휘를 다 갖는다

```
readiness_coverage    6축       후보 선정 — 어느 고객에게 필요한가
assessment_coverage   평가영역   선행 판정 — 어떤 ISV 전제를 푸는가
assessment_lift       평가영역   그 전제를 얼마나 올려주는가
```

엔진에서 `rawCoverage`(점수 계산)와 `enablerCoverage`(번들 선행)를 **분리한 이유가
이것이다.** 한 필드에 두면 후보 점수가 이중 계산된다.

- `P01`·`P04` 의 `assessment_lift` 는 **비어 있다.** 전략·조직 과업이라 제품 게이트를
  풀지 않는다 — 넣으면 "컨설팅을 하면 SSO 가 생긴다"가 된다
- **`lift` 를 합산하지 않는다.** 두 패키지를 합쳐도 준비도가 더 올라가지 않는다.
  큰 값을 쓴다

## 선행 패키지는 실제로 덮어야 한다

「이 패키지를 넣으면 점수가 오른다」가 아니라 **막힌 전제를 실제로 다루는가**로 고른다.
`strengthFor` 는 후보의 `enablerCoverage` 를 보고, 거기 그 영역이 없으면 상승폭(`lift`)이
아무리 커도 선행으로 쓰지 않는다. 상승폭으로 고르면 화면에는 "이걸 먼저 하면 전제가
풀립니다"라고 뜨는데 그 패키지가 해당 영역을 **손도 안 대는** 상황이 실제로 있었다.

같은 전제를 여럿이 풀 수 있으면 **가장 깊게 다루는 쪽**(`strength`)이 이긴다 — 먼저 찾은
것을 쓰면 DB 가 행을 돌려주는 순서에 추천이 달라진다.

## 42 → 10 은 8개만 찬다 (037 bridge)

못 채우는 둘은 `A02 저장·보존` · `A03 계정·접근통제`. SSO·SCIM·보존기간 같은 **제품
설정**이라 42문항이 묻지 않는다. STEP03 에서 후보별로 확인한다.

여러 문항이 한 영역을 채우면 **평균**이다. 최댓값이면 하나만 잘해도 통과하고, 최솟값이면
하나만 못해도 막힌다.

**`replit` 은 대응 평가영역이 없다.** 알려진 누락이라 검사에 이름을 박아 뒀다 — 다른 게
조용히 빠지면 실패한다.

## 처방과 오퍼링을 가른다

`readiness_items.fix`(043)는 **고객이 받는 문서에 그대로 들어간다.**

- 한 문장 · 행동 동사로 시작 · **제품명 금지**
- "AIR Service 를 사세요"가 아니라 "데이터 품질 자동 점검 규칙부터 만드세요"
- "이 일을 우리가 돕습니다"는 **그 아래 따로** 붙는다

섞으면 리포트가 광고가 되고 신뢰를 잃는다. 이 시스템이 가장 피하는 실패다.

## `/radar` 는 창이지 원본이 아니다

SSOT 는 DB 다. `/radar` 는 `slot`·`coverage`·`red_flags` 를 안 그린다 — "왜 이게 추천이
안 됐나"는 거기서 답할 수 없다. `/admin` 의 「추천 vs 채택」이 그 자리다.
