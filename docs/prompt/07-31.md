## 0-1. 작업은 두 덩어리다

차트는 **되면 하고 안 되면 안 하는 것**으로 시작했다. 그래서 아래를 갈라 놓았다 — 왼쪽은 차트와 무관하게 굴러가고, 오른쪽은 차트를 접으면 **통째로 사라지는** 것들이다.
검토 결과 **오른쪽도 하기로 방침이 섰고**(6축을 제대로 채운다), 그래서 §3 을 그 기준으로 다시 짰다. 다만 **왼쪽이 오른쪽에 묶여 늦어지지 않도록** 구분은 그대로 둔다.

| | **A. 차트와 무관 — 그냥 한다** | **B. 6축·차트 묶음** |
|---|---|---|
| | ① 솔루션 hidden 토글 (§4-3) | ④ **6축 배정** (§3-1) |
| | ② 기본정보 입력칸 확장 (§4-2) | ⑤ **신규 문항 2~3개** (§3-1b·§3-1c) |
| | ③ **랜딩 문항 주체 분리** (§1·§3-2) | ⑥ 레이더차트 (§4-1) |
| 성격 | 요청 2건 + 데이터 품질 결함 1건 | 표현 개선 |
| 접으면 | — | 잔여 작업 0 |

> **③ 은 차트 때문에 나온 게 아니다.** 고객이 답할 수 없는 7문항을 물어서 "모르니까 3점"이 추천 판정에 쓰이고 있는 문제다(§1). 차트를 영영 안 해도 고쳐야 한다.
> 반대로 **④⑤⑥ 은 한 덩어리**다. 셋 다 하거나 셋 다 안 하거나다 — 6축을 제대로 채우지 않으면 레이더가 찌그러지고, 레이더를 안 그리면 6축 배정을 할 이유가 없다.

> 📌 **방침: B 덩어리는 「제대로」 간다.** 6축이 전부 유의미하게 채워지도록 §3 을 다시 짰다.
> ④ 는 **신규 문항 없이** 재배정만으로 G 4→3 · T 1→3 · P 2→3 이 되고, ⑤ 는 **B축 3개 + T축 1개**만 남는다. 그중 B축 1개는 메일의 「AI 도입 단계」가 대체하므로 **실제 신규 문항은 2~3개**다.
> ⑤ 는 **새 카테고리 `E` 로 넣어 추천엔진 영향을 0 으로 만든다** (§3-1c).

## 1. 문항이 잘못된 게 아니라, **묻는 대상이 어긋나 있다**

체크리스트 21문항은 **딜 진행 가능 여부를 판정하려고** 만든 것이고, 그 목적에는 정확하다.
문제는 하나뿐이다 — **랜딩(`/offering`)이 이 21개를 전부 고객에게 직접 묻고 있다** (`offering.js:50` renderQuestions, A→B→C→D 순회).

### 1-1. 고객이 판단할 수 없는 7문항

| 문항 | 실제 질문 (001 시드 원문) | 왜 PreSales 항목인가 |
|---|---|---|
| **A-3** 보안 게이트웨이 준비도 | AI 트래픽을 통제할 보안 경로가 있나요? | SWG·프록시·DLP 구성 — 보안팀 영역 |
| **A-4** 감사 로그와 추적성 | 질의·응답·관리 변경 이력을 남길 수 있나요? | 중앙 로그·보존기간 설계 — 인프라 영역 |
| **B-9** 개발·테스트 환경 | 격리된 개발·검증 환경이 있나요? | 개발조직 내부 사정 |
| **B-10** 확장성·성능 기준 | 예상 사용자와 응답시간 기준이 있나요? | 용량 산정을 해본 적 없으면 답 자체가 없다 |
| **B-11** 모델·벤더 전환성 | 특정 모델 종속을 통제할 수 있나요? | 모델 라우팅·추상화 계층 — 개념 자체가 전문 영역 |
| **C-13** 품질 평가 체계 | 정확도·안전성 평가 기준이 있나요? | 평가셋·합격 기준 설계 |
| **C-16** 변경·배포 관리 | 프롬프트·모델 변경을 통제하나요? | 프롬프트 버전·롤백 절차 |

> ✅ **7개 전부 PreSales 가 판단할 항목이다.**
> 이건 체크리스트가 **판정 도구로 정확히 설계됐다는 증거**지 결함이 아니다. 잘못 놓인 것은 문항이 아니라 **질문을 받는 사람**이다.

### 1-2. 어긋남이 만드는 결과

모르는 질문을 받으면 **가운데를 찍는다.** 그 3점이 `fqa_scores` 에 담겨 그대로 딜로 들어가고, **추천엔진의 전제조건 판정에 쓰인다.** 근거 없는 숫자가 게이트를 열거나 막는다.

> 🚨 계산해 보면 이 7문항 때문에 **강한 고객과 약한 고객의 격차가 31% 압축된다** (§3-1e).
> 문항이 많아서 정밀한 게 아니라, **엉뚱한 사람에게 물은 문항이 정밀도를 깎고 있다.**

## 2. 재정의 — 배정은 "축"이 아니라 "층"이다

앞선 검토는 21문항을 6축에 배정하는 문제로 봤다. 방향이 틀렸다. 올바른 배정은 **응답 주체가 1차 기준**이고 축은 그 다음이다.

| | 랜딩 `/offering` | 허브 `/hub` |
|---|---|---|
| **누가 답하나** | **고객** | **영업 (+PreSales)** |
| **무엇을 묻나** | 회사 수준 — 방향·조직·데이터·업무 현황 | 구축 수준 — 통제·연동·운영 스펙 |
| **표현 축** | **6축 레이더 + 벤치마크 + 성숙도** | **4축 게이트** A/B/C/D |
| **결과의 쓸모** | 대화 시작 · 리드 생성 | 추천·번들·딜사이즈 판정 |
| **미응답** | 비워두는 게 정상 | 영업이 채운다 |

**두 화면이 같은 `fqa_scores` 를 공유한다.** 고객이 채운 칸은 영업이 다시 묻지 않고, 영업은 **빈칸과 고객이 못 답한 칸만** 채운다. 이 파이프는 이미 있다.

### 그래서 AIR-N 6축의 정체

S(전략) · P(인재) · D(데이터) · T(플랫폼) · B(프로세스) · G(거버넌스) — 전부 **"우리 회사가 어떤 상태인가"** 질문이지 **"무엇을 구축했는가"** 질문이 아니다. FQA 4축은 정반대다.

> **AIR-N 6축은 새 진단이 아니라, 고객이 답할 수 있는 언어다.**
> 두 개의 진단이 아니라 **한 진단의 두 층**이다. 중첩을 걱정할 게 아니라 층을 나누면 된다.

### 3-1c. 신규 문항을 DB 어디에 넣나 ⚠️

`fqa_items` 는 `category`(A/B/C/D)를 반드시 갖는다. **어디에 넣느냐가 추천엔진을 건드린다.**

| 안 | 방식 | 영향 |
|:---:|---|---|
| ✕ | 기존 A~D 에 끼워 넣기 | 해당 카테고리 **평균 계산 바구니가 바뀐다.** 012·017 에서 맞춰 둔 전제조건 임계값의 의미가 달라진다 |
| ✅ | **새 카테고리 `E`(성숙도) 신설** | 전제조건에 **쓰지 않는다.** A~D 평균은 그대로 → **추천엔진 영향 0** |

**`E` 로 갈 때 같이 손봐야 할 곳** (안 고치면 티가 난다)

```
hub.js:597    ['A','B','C','D'] 하드코딩 → E 가 점수카드에 안 뜬다
hub.js:1034   failing 계산이 fqa_totals 전체를 훑는다
              → E 가 "보완 필요" 로 잡혀 제안 문구에 끼어든다.  E 는 제외해야 함
offering.js:3 CATEGORY_LABELS 에 E 없음
```

> **핵심 원칙: E 는 보여주는 값이지 판정하는 값이 아니다.** 레이더를 그리는 데 쓰고, 딜 진행 가능 여부에는 쓰지 않는다.

## 4. 요청 3건의 배치

### 4-1. 랜딩 차트 — 6축 레이더, **결과 화면에만**

**기술적으로는 된다.** 막는 건 없다.
- AIR-N 이 라이브러리 없이 260px `<canvas>` 로 직접 그린다. 우리도 같은 방식이면 **CDN 추가 0 · 100줄 안팎**
- `offering.js` 는 이미 공개 자산으로 무인증 서빙된다 (`server.js:1781`). 붙일 자리가 이미 있다
- 붙일 곳: `#result-summary`(현재 요약 문구 1줄) · `#result-grid`(현재 A/B/C/D 카드 4장)

#### 언제 보여주나 — **마지막에 계산된 데이터만**

**실시간 갱신은 하지 않는다.** AIR-N 은 문항 하나 답할 때마다 레이더를 다시 그린다 (`updateDiag()` 끝에서 매번 `drawDiagRadar()` 호출). **그 방식은 따라가지 않는다.**

| | AIR-N | 우리 |
|---|---|---|
| 그리는 시점 | 문항 응답할 때마다 | **결과 계산 1회** |
| 미완성 상태 | 고객에게 보임 | **안 보임** |
| 점수 계산 주체 | 브라우저 | **서버** |

**지금 구조가 이미 그렇다.** `#result` 섹션은 `hidden` 이고 「결과 계산」 버튼을 눌러야 열린다. 그리고 **모든 영역에 답해야 계산된다** (`offering.js:145` — `categories().every(categoryComplete)` 미충족 시 거부). 즉 부분 응답 상태의 도형이 나올 일이 애초에 없다.
→ 차트는 `calculateResult()` 성공 직후 `#result` 안에서 **한 번 그리고 끝**. `resize` 재드로잉만 붙이면 된다.

> ✅ **부수 효과 — 「나」안이 쉬워진다.** B축이 비어 도형이 찌그러지더라도, 고객이 보는 건 **완성된 결과 하나**뿐이다. 답하는 도중에 이상한 모양이 실시간으로 보이는 일이 없다.

⚠️ **대신 API 를 손봐야 한다.** `POST /api/hub/public/diagnose` 는 지금 A/B/C/D 만 돌려준다 (`routes/hub.js:191~209`).
→ 6축(또는 5축) 점수도 **서버가 계산해서 내려주게** 한다. 매핑은 DB 에 두고 브라우저는 받아서 그리기만 한다.
**클라이언트가 따로 계산하면 안 된다** — 랜딩에서 본 숫자와 허브·제안서의 숫자가 갈라지는 순간 §5 의 전제가 깨진다.

**막히는 건 기술이 아니라 데이터였다.** 셋 중 하나를 고르는 문제였고, **「다」로 간다.**

| 안 | 내용 | 판정 |
|:---:|---|---|
| 가 | 안 한다 | — |
| 나 | 지금 데이터로 그린다 (5축 또는 B 미측정) | B축이 비어 도형이 찌그러진다 |
| **다** | **6축을 제대로 채우고 그린다** | ✅ **채택** — §3 재배정 |

**「다」가 처음 봤을 때보다 가벼워졌다.**

| | 초안 | §3 재배정 후 |
|---|:---:|:---:|
| 신규 문항 | 4~5개 | **2~3개** (B축 1개는 기본정보 「AI 도입 단계」로 대체) |
| 미배정 문항 | 2개 | **0개** |
| 축 균형 | G 4 / T 1 / B 0 | **전 축 3** |
| 추천엔진 영향 | 검토 필요 | **0** (카테고리 `E` 분리 · §3-1c) |

**그리는 것**
- 6축 레이더 — 축 라벨은 `S 전략 / P 인재 / D 데이터 / T 플랫폼 / B 프로세스 / G 거버넌스`
- 종합점수 + 성숙도 5단계 (AIR-N 기준: 초기 1.0~1.9 / 준비 2.0~2.9 / 정착 3.0~3.9 / 확산 4.0~4.7 / 최적화 4.8~5.0)
- 하위 3축 우선순위 — **여기에 `readiness_lift` 문구를 붙인다** (아래 💡)

⚠️ **벤치마크 수치는 어느 안이든 별건이다.** AIR-N 은 하드코딩 상수를 쓴다 (업계평균 `[3.0, 2.8, 3.5, 3.2, 3.1, 2.9]`). 코드에 출처가 없다.

> 💡 **부수 효과는 그대로 살아 있다.** `stack[]` · `interests[]` 는 추천엔진의 **실질 입력**이 된다.

> ⚠️ **벤치마크와의 연결.** 업종 벤치마크를 **랜딩 결과 화면에서** 보여주려면 산업이 고객 입력이어야 한다(위 표대로).

## 5. 왜 이 동선이어야 하나

1. **고객이 랜딩에서 자기 상태를 6축 레이더로 본다** → 결핍이 눈에 보인다. "우리가 B축이 1.2구나"
2. **그 답이 그대로 딜이 되어 영업에게 간다** → 영업은 고객이 못 답한 7문항만 채운다. 처음부터 다시 묻지 않는다
3. **채우면 추천이 뜬다** → 전제에 막히면 패키지를 선행으로 붙여 *"02 AI Trust 선행 시 A 1.8 → 3.3 (전제 3 충족)"* 로 제안한다

> 🎯 **핵심은 랜딩의 레이더와 허브의 게이트가 같은 숫자를 쓴다는 것이다.**
> 고객이 화면에서 본 1.8 과 제안서에 적힌 1.8 이 같아야 신뢰가 생긴다.
> **진단을 둘로 나누면 이게 깨진다.** 그래서 합치는 게 아니라 층을 나누는 것이다.
