# 카탈로그 운영 기획 — 영업 전원 사용 + ISSU 자율 등록

작성 2026-07-28 · 관련 마이그레이션 `013` · 설계 연계 `recommendation-engine-design.md`

## 0. 전환의 핵심

지금까지는 사람이 `.docx` 를 쓰고 누군가 DB 에 옮겼다. 그 방식이 22종에서 이미 무너져 있다 —
9종만 상세 작성됐고, 7종은 `{name}` 플레이스홀더가 치환되지 않은 채 프로덕션에 들어가 있으며,
그 7종은 §3.2 페르소나 문장이 글자 하나 다르지 않게 동일하다.

```
지금:  ISSU가 문서 작성 → 누군가 DB 이관 → 드리프트 → {name} 사고
목표:  ISSU가 /admin 에서 직접 등록 → 시스템이 완성도 검사 → 통과해야 발행
```

**자유 입력만 주면 같은 사고가 반복된다.** 등록 권한을 여는 것과 품질 게이트를 세우는 것은
한 세트여야 한다.

## 1. 역할

역할은 사람이 아니라 하는 일로 정의한다. 지금은 curator 와 admin 이 같은 사람이겠지만,
ISSU 담당자가 늘면 코드 수정 없이 붙는다.

| 역할 | 대상 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|---|
| `viewer` | **영업 전원** | hub 딜 작업 · 추천 소비 · `/radar` 카탈로그 읽기 | 카탈로그 편집 · 내부 본문 열람 |
| `curator` | **ISSU (ISV 담당)** | 솔루션 등록·수정·발행 · 판정 데이터 입력 · **`opinion`·`sections_internal` 편집** · 포컬 관리 · 버전 이력 조회 | **회원 승인 · 실단가 확정 · 롤백 · 감사로그** |
| `admin` | 시스템 관리 | 전부 | — |

### 결정 사항

- **curator 는 내부 본문(마진·리셀러 전략)을 본다.** ISV 담당자가 등록할 때 마진 코멘트까지
  한 번에 쓰는 편이 자연스럽고, 두 단계로 나누면 등록이 늘어진다. 대신 마진 정보 접근자가
  늘어나므로 curator 발급은 admin 이 통제한다.
- **영업(`viewer`)의 `/radar` 접근은 유지한다.** 딜과 무관하게 카탈로그를 탐색할 수 있어야
  영업이 학습한다. 내부 문단은 `lib/section-privacy.js` 가 런타임에 제거하므로 노출되지 않는다.
- **curator 가 직접 발행한다.** 애초 안은 "발행 요청 → admin 승인"이었으나, 사람 승인 큐는
  병목이 되고 실제 통제력도 약하다. **완성도 게이트가 진짜 통제 장치**다.
- **회원 승인은 수동을 유지한다.** 다만 "영업 전원"이면 초기 일괄 등록이 필요하므로
  `/admin` 회원 관리에 일괄 승인을 추가한다(현재 1건씩).

### 경계는 서버에 있다

프론트에서 탭을 감추는 것은 편의일 뿐이다. 실제 경계는 `server.js` 의 `adminOnly` /
`catalogEditorOnly` 미들웨어와, 가격 필드의 함수 단위 가드다. 가격은 생성·수정·발행 세 경로
전부에서 막았다 — 발행 경로로 우회되지 않게 하기 위함이다.

## 2. ISSU 등록 워크플로

```
① 신규 등록      슬롯 선택 → 기본 메타 → sections 8개 → 판정 데이터
② 완성도 검사    자동. 미달 항목을 목록으로 표시
③ draft 유지     통과할 때까지
④ 발행           curator 가 직접
```

## 3. 완성도 게이트 (2-2c)

발행 전 자동 검사. 오늘의 사고를 구조로 차단한다.

| 검사 | 기준 | 실패 시 |
|---|---|---|
| 슬롯 배정 | `slot` 필수 | **차단** |
| 갭 커버 | `fqa_coverage` ≥ 1 | **차단** — 없으면 추천 후보가 되지 않는다 |
| 전제 조건 | `prerequisites` ≥ 1 또는 "없음" 명시 | **차단** |
| 플레이스홀더 | `{name}` `{{` `TODO` `TBD` 검출 | **차단** |
| 템플릿 복붙 | 타 솔루션과 §3.2 문장 완전일치 | **차단** |
| 레이어 정합 | `layer` = 슬롯의 `layer` | **차단** |
| 산업 적합도 | §3.1 에 ○ 최소 1개 | 경고 |
| 본문 분량 | §1 ≥ 500자, §7 ≥ 300자 | 경고 |
| red_flags slug | 가리키는 슬러그가 실재 | **차단** |

"템플릿 복붙 검출"이 특히 중요하다. 7종이 동일 문장을 쓰고 있었고 이건 기계적으로 잡힌다.

## 4. 커버리지 대시보드 (2-2d)

ISSU 가 "무엇을 더 넣어야 하는지" 스스로 알아야 한다.

```
슬롯 커버리지                   FQA 항목 커버리지
L0 data-platform    0종 ⚠      A3 보안 게이트웨이   2종
L0 vector-store     0종 ⚠      D5 예산·구매 준비도  0종 ⚠
L1 llm-platform     3종         B5 모델·벤더 전환성  1종 ⚠
L4 security-gateway 2종         ...
```

오늘 손으로 찾아낸 공백(L0 전체, D5, B5)을 상시로 보게 된다.

## 5. 영업 쪽 — 확산과 피드백

| 항목 | 현재 | 계획 |
|---|---|---|
| 계정 | 수동 승인, 1건씩 | 수동 유지 + **일괄 승인** |
| 추천 소비 | STEP03 수동 선택 | 추천 + 근거, 수동 선택 병행 유지 |
| 피드백 | 없음 | `recommendation_snapshot` vs 실제 `isv_combo` 대조 |
| 학습 | — | 근거 문장이 곧 교육 자료 |

피드백은 ISSU 에게 돌아간다. **"추천됐는데 영업이 안 고른 솔루션"은 콘텐츠나 판정 데이터에
문제가 있다는 신호**다.

## 6. 콘텐츠 보강 — 하이브리드

```
ISSU  →  등록 대상 리스트 제공
  ↓
초안  →  리서치 + 8섹션 + 판정 데이터 추출 (Portal26 방식)
  ↓
ISSU  →  검토·수정 → 발행
```

당면 대상 12종:

| 그룹 | 대상 |
|---|---|
| Trust Layer 3 | Zscaler · Check Point · New Relic (Portal26 은 초안 완료) |
| 껍데기 9 | IBM · DataRobot · CNVRG · Unique · Tigergraph · MeshyAI · H2O · FollowerRabbit · Wand.ai |

`/radar` 시뮬레이터가 추천하는 미등록 22종(Databricks·Snowflake·ServiceNow·MZC AIR Platform
등)은 2차 범위 밖이다. 슬롯 체계는 그 22종까지 수용하도록 정의해뒀으므로 나중에 추가해도
재작업이 없다.

## 7. 규모 대응

- 슬롯 체계는 44종 기준이라 당장은 버틴다
- `solution_slots` 도 ISSU 가 추가할 수 있어야 한다 (현재는 마이그레이션으로만 가능)
- 카탈로그 목록 UI 는 22종 기준. 100종에서는 슬롯별 그룹핑·검색 강화가 필요하다
