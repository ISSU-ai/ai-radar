# 오퍼링을 만드는 기준

> 2026-08-19 · 2027 BP Supply-centric 대응.
> **ISSU 는 ISV BU 의 이전 이름이다.** 이 문서는 새 이름을 쓴다.

---

## Context — 왜 기준이 먼저인가

2027 BP 가 **Supply-centric** 으로 간다. 「무엇을 팔 것인가(Supply)」를 먼저 정의하고
그다음 「얼마나 팔 것인가(Demand)」다. Wave 1 의 산출물 이름이 그대로
**「Sellable Portfolio Book」** — **팔 수 있는 것**의 목록이다.

그런데 「팔 수 있다」의 뜻이 정해져 있지 않다. 그래서 지금 필요한 것은
**분류표가 아니라 판정 기준**이다.

- 분류표(카테고리 체계)는 이미 「반영 완료」됐고 8/28 에 온다 — **우리가 만들 것이 아니다**
- **기준은 분류표가 무엇이든 그대로 산다.** 먼저 만들 수 있고, 만들어 두면
  8/28 에 온 목록을 그 자리에서 판정할 수 있다

BU 통합의 배경도 같은 말을 한다 — *"고객 과제가 단일 솔루션으로 끝나지 않고
영업·컨설팅·구축·운영이 하나의 흐름으로 연결된다"*. 그러면 **오퍼링은 제품이 아니라
「끝까지 책임지는 단위」**여야 한다.

---

## 1. 구분 — 축 셋

오퍼링 하나는 **세 축의 좌표**로 정해진다. 하나라도 비면 팔 수 없다.

### 축 A · 유형 — 무엇을 파는가

MZC 정의를 그대로 쓴다.

| | |
|---|---|
| **Product** | 벤더/ISV 로부터 공급받아 파는 제품 |
| **Service** | 사람이 하는 구축·PoC·컨설팅·운영 (PS / MS) |
| **Solution** | 제품 + 서비스. MZC 기술역량·프로젝트경험·방법론으로 구조화한 **MZC 만의 해법** |

### 축 B · 공급 — **누가 딜리버리하는가**

**Supply-centric 의 1번 축이다.** BU 가 솔루션 영역별 Unit 으로 나뉘어 있고,
그게 곧 딜리버리 주체다.

```
ServiceNow          ITSM · AX
Salesforce          CRM
Platform Engineering 플랫폼
Data & AI           데이터 · AI
Hybrid Cloud        하이브리드 클라우드
CaaS                컨테이너
```

여기에 **공통 지원 조직**이 붙는다 — 얼라이언스·GTM·마켓플레이스(MPN)·
크로스셀링·오퍼링 기획·수주관리.

> **BU 통합의 핵심이 이 축에 있다.** 「CRM·ITSM·플랫폼을 함께 검토하는 고객」이란
> **여러 Unit 이 한 딜에 들어온다**는 뜻이다. 그래서 오퍼링에는
> **주 딜리버리 Unit** 과 **참여 Unit** 이 따로 적혀야 한다.

### 축 C · 적용 — 어디에 파는가

**Vertical**(산업)과 **Horizontal**(도메인). MZC 정의가 Solution 을 설명하며 직접
말하는 축이다. 카탈로그에 `industries` 가 이미 있다.

---

## 2. ⚠ 지금 시스템이 모르는 것 — 축 B

카탈로그(`solutions`)가 아는 것과 모르는 것을 대조하면 이렇다.

| 오퍼링이 답해야 할 것 | 카탈로그에 있나 |
|---|---|
| 무엇을 해결하나 | ✅ `jtbd` |
| 어떤 제품인가 | ✅ `slot` · `layer` · `category` |
| 어느 산업인가 | ✅ `industries` |
| 얼마인가 | ✅ `list_price` · `price_is_placeholder` |
| 언제 팔면 안 되나 | ✅ `red_flags` |
| 고객 쪽 전제 | ✅ `prerequisites` |
| **누가 딜리버리하나** | **✗ 없다** |
| **유형(Product/Service/Solution)** | **✗ 없다** — 지금은 Product 만 있다 |

**「누가 만드나」를 모르는 채로는 Supply-centric 포트폴리오가 성립하지 않는다.**
팔고 나서 만들 사람을 찾게 되고, 그게 지금 문제의 원인이다.

---

## 3. 오퍼링 성립 기준 — 일곱

각 오퍼링은 아래 일곱에 답해야 한다. **넷은 필수, 셋은 권장.**

### 필수 넷 — 하나라도 비면 **팔 수 없다**

| | 질문 | 없으면 |
|---|---|---|
| **1** | **주 딜리버리 Unit 이 지정됐나** | 팔고 나서 만들 사람을 찾는다 |
| **2** | **유형이 Product / Service / Solution 중 무엇인가** | 견적 방식이 안 정해진다 |
| **3** | **어떤 고객 문제를 해결하나** (한 문장) | 영업이 설명을 못 한다 |
| **4** | **가격 모델이 있나** (실단가 또는 산정 방식) | 딜 사이즈를 못 낸다 |

⚠ **4는 「금액」이 아니라 「모델」이다.** 「MD × 단가」·「사용자당 연 단위」처럼
**계산하는 법**이 정해져 있으면 충족이다. 실단가 미확정은 「별도협의」로 팔 수 있다.

### 권장 셋 — 없으면 **조건부**

| | 질문 | 없으면 |
|---|---|---|
| **5** | **왜 MZC 인가** — 우리 방법론·경험이 어디에 들어가나 | 단순 리셀이라 마진이 얇고 대체된다 |
| **6** | **언제 팔면 안 되나** — 부적합 신호 | 영업이 고객 앞에서 못 지킬 약속을 한다 |
| **7** | **고객 쪽 전제는 무엇인가** | PoC 에서 깨진다 |

## 4. 판정 — 세 단계

기준을 적용하면 모든 항목이 셋 중 하나가 된다.

```
Sellable      필수 4 + 권장 3  →  Portfolio Book 에 올린다
조건부         필수 4만          →  올리되 「확인 필요」를 같이 적는다
카탈로그 항목   필수에 구멍       →  판매 목록이 아니다. 정보로만 둔다
```

**「카탈로그 항목」은 실패가 아니다.** 255종 벤더 마스터의 대부분이 여기 있을 것이고,
그게 정상이다. **취급한다는 것과 오퍼링으로 판다는 것은 다르다** — 이 구분이 없으면
Portfolio Book 이 벤더 목록이 되고 아무도 안 쓴다.

⚠ **필수 4를 못 넘는데 Sellable 로 올리지 않는다.** 특히 **1번(딜리버리 Unit)** 이
비어 있는 것을 「일단 올려 두자」로 넘기면, 그게 나중에 수주하고 못 만드는 딜이 된다.

---

## 5. 기존 5대 오퍼링을 이 기준으로 다시 보면

지금 `offerings` 표에 01~05 가 있는데 **전부 AI 한정**이고 축 B 가 비어 있다.

| | 필수 1 (Unit) | 필수 2 (유형) | 상태 |
|---|---|---|---|
| 01 AI Consulting | 미기재 | Service (PS) | **조건부** — Unit 지정 필요 |
| 02 OpenAI Ready | 미기재 | Solution | **조건부** |
| 03 AIR Service | 미기재 | Service | **조건부** |
| 04 Adoption & Change | 미기재 | Service | **조건부** |
| 05 (확장) | 미기재 | — | 확인 필요 |

**다섯 다 축 B 만 채우면 Sellable 이 된다.** 내용은 이미 있다 —
`packages` 에 기간·대상·역할이 있고 `readiness_coverage` 로 어느 고객에게 맞는지도 안다.

> Data & AI 영역 오퍼링이라면 주 딜리버리는 **Integrated Solution CoE 의 Data & AI**,
> 참여는 **Platform Engineering**(인프라 구축 시)·**ISV EcoSystem**(마켓플레이스 경유 시)
> 같은 식으로 적힌다. 이 한 줄이 없어서 지금 「누가 하느냐」가 매번 협의 대상이다.

---

## 6. 8/28 카테고리 체계와의 관계

**충돌하지 않는다. 층이 다르다.**

```
8/28 카테고리 체계   ←  분류표. 어느 칸에 넣을지
이 문서의 일곱 기준   ←  판정. 팔 수 있는 것인지
```

카테고리가 무엇으로 오든 기준은 그대로 쓴다. 오히려 **8/28 목록을 받자마자
이 기준으로 훑으면 「Sellable 이 몇 개인가」가 그날 나온다.**

그리고 이 기준이 곧 **임포트 검증 규칙**이 된다 — 엑셀에서 들어온 행이
필수 4를 채웠는지 미리보기에서 세면, 검토 대상이 자동으로 좁혀진다.

---

## 7. 그래서 시스템에 필요한 것 둘

기준을 정하고 나면 카탈로그에 두 칸이 빈다.

| | |
|---|---|
| **`delivery_unit`** | 주 딜리버리 Unit + 참여 Unit. **축 B** |
| **`offering_type`** | Product / Service / Solution. **축 A** |

⚠ **지금 만들지 않는다.** 8/28 에 오는 체계가 이 이름을 다르게 쓸 수 있다.
임포트를 설계할 때 **자리만 비워 둔다**(기존 계획의 「`kind` 자리를 비워 둔다」와 같은 것).

---

## 다음에 정할 것

1. **Unit 목록의 확정 명칭** — 조직도 표기 그대로 쓸지, 축약할지
2. **참여 Unit 을 몇 개까지 적을지** — 다 적으면 아무 뜻이 없다. 둘까지를 권한다
3. **「조건부」를 Portfolio Book 에 넣을지** — 넣으면 목록이 커지고, 빼면 진행 중인 것이 안 보인다
4. `ISSU → ISV BU` 이름 정리 — 코드·문서 **20여 파일**에 걸쳐 있고 화면 제목
   (`ISSU Enablement Hub` · `ISSU Radar`)도 포함이라 **제품 명칭 결정이 먼저다**
