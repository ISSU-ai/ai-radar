```
21문항 ─→ fqa_totals (카테고리 가중평균)
              ↓
          analyseGaps()   미달 여부 · 미달 폭 · 응답 신뢰도
              ↓
후보 점수 = 0.40 × gap_fit      ← fqa_coverage 가 미달 카테고리를 얼마나 덮나
```

## 2. 42문항을 6축·오퍼링에 붙이면

### 2-1. 축 → 오퍼링이 거의 1:1 로 붙습니다

진단기준 엑셀「진단 결과」시트가 이미 이 매핑을 갖고 있고, 42문항 내용과도 맞습니다.

|:---:|---|---|

**축이 곧 오퍼링에 가깝다**는 것이 이 설계의 강점입니다. 210개(42×5) 셀을 다 채울 필요 없이 **문항당 1~2개 오퍼링**만 지정하면 됩니다.

### 2-2. 점수 계산

낮은 준비도 = 그 오퍼링이 필요하다는 신호입니다.

```
gap(q)          = max(0, target − answer(q))        target 기본 4 (5점 만점)
score(offering) = Σ_q  weight(q, offering) × gap(q) × confidence(q)
                  ─────────────────────────────────────────────────
                            Σ_q  weight(q, offering) × target

confidence(q)   = 응답자 유형이 맞으면 1, "모르겠음"이면 0
```

**정규화가 필요합니다.** 오퍼링마다 걸린 문항 수가 다릅니다(01 은 S축 7문항, 05 는 4문항 안팎). 나누지 않으면 문항이 많은 오퍼링이 항상 이깁니다.

## 4. 가장 큰 쟁점 — **누가 답하나**

42문항은 응답자가 나뉘어 있습니다. 문항마다 `respondent` 필드가 박혀 있습니다.

| 응답자 | 문항 수 | 범위 |
|---|:---:|---|
| **IT담당** | **20** | D1~D7 · T1~T7 · B3 · B7 · G2 · G3 · G6 · G7 |
| **경영진** | **15** | S1~S7 · P1 · P4 · P6 · P7 · B5 · G1 · G4 · G5 |
| 현업 | 6 | P3 · P5 · B1 · B2 · B4 · B6 |
| 전직원 | 1 | P2 |

**한 사람이 42문항을 다 답할 수 없습니다.** AIR-N 은 애초에 그렇게 설계되지 않았습니다 — 4주 프로세스로 W1 전사 설문, W2 CIO/CDO 인터뷰를 돕니다.

웹폼에서 한 명이 앉은자리에 답하면 **자기 영역 밖 문항은 추측이 됩니다.** 그러면 §1 에서 이미 확인한 문제가 21문항이 아니라 42문항 규모로 재현됩니다 — 모르면 가운데를 찍고, 그 3점이 오퍼링 점수를 결정합니다.

> **이건 기술로 못 푸는 문제입니다.** 설문 운영 방식을 정해야 합니다. §6 에 선택지를 적었습니다.

## 5. 권고 설계 — 갈아끼우지 말고 층을 얹습니다

```
┌─ 42문항 (신규) ────────────────────────────────────────┐
│  응답자별 수집 → 6축 점수 → 가중치 → 오퍼링 5종 순위      │
│  "이 회사에는 03 AIR Service 가 가장 급하다"             │
└────────────────────────┬───────────────────────────────┘
                         │  6축 → 21문항 매핑 (§3, ◎○ 13개)
                         ↓  나머지 8개는 영업이 채운다
┌─ 21문항 (유지) ────────────────────────────────────────┐
│  카테고리 게이트 → ISV 전제조건 판정 → 선행 패키지 번들   │
│  "Claude 를 팔려면 A-2 가 3 이어야 한다. 지금 1.8 이니   │
│   02 를 먼저 붙이면 3.3 이 된다"                        │
└────────────────────────────────────────────────────────┘
```

**왜 이렇게 나누나**

| | 42문항 | 21문항 |
|---|---|---|
| 묻는 것 | 회사가 AI 를 얼마나 하고 있나 | 이 제품을 지금 살 수 있나 |
| 답하는 사람 | 고객사 경영진·IT·현업 | 영업·PreSales |
| 산출 | **오퍼링 순위** (우리 서비스) | **ISV 가부 + 선행 패키지** |
| 성격 | 눈금자 | 게이트 |

**두 층이 이어지는 지점**: §3 의 ◎○ 13개는 42 응답에서 21 점수를 자동으로 채웁니다. 나머지 8개(✕ 4 + △ 4)는 영업이 허브에서 채웁니다 — 이미 만들어 둔 "고객 미응답" 배지가 그 자리입니다.

## 6. 데이터 모델

### 6-1. 새 표 3개

```sql
-- 42문항 본체. fqa_items 와 별도로 둔다. 축·응답자·루브릭이 있어 구조가 다르고,
-- 섞으면 21문항에 걸린 전제조건이 흔들린다.
create table readiness_items (
  code        text primary key,          -- 'S1' … 'G7'
  area        text not null,             -- S/P/D/T/B/G
  seq         int  not null,
  respondent  text not null,             -- exec | it | staff | all
  text        text not null,
  detail      text,                      -- 확인사항
  rubric      jsonb not null default '[]'::jsonb,   -- 1~5점 행동 기준
  target      numeric not null default 4,           -- 이 점수 이상이면 갭 없음
  weight      numeric not null default 1,           -- 축 내 상대 중요도
  status      text not null default 'active'
);

-- 문항 → 오퍼링 가중치. 210 셀 중 실제로 채우는 건 60~80 개다.
create table readiness_offering_weights (
  item_code   text not null references readiness_items(code) on delete cascade,
  offering_id text not null references offerings(id) on delete cascade,
  weight      numeric not null,          -- 0~1. 이 문항이 그 오퍼링을 얼마나 부르나
  rationale   text,                      -- 왜 이 가중치인가. 없으면 블랙박스가 된다
  primary key (item_code, offering_id)
);

-- 42문항 → 21문항 대응. §3 의 ◎○ 만 넣는다. △✕ 는 넣지 않는다.
create table readiness_fqa_bridge (
  item_code    text not null references readiness_items(code) on delete cascade,
  fqa_category text not null,
  fqa_item     text not null,
  fidelity     text not null,            -- exact | good — △ 이하는 아예 안 넣는다
  primary key (item_code, fqa_category, fqa_item)
);
```

### 6-2. 딜에 붙는 것

```sql
alter table deals add column readiness_scores jsonb not null default '{}'::jsonb;
--   {"S1": 3, "S2": 2, ...}  응답 원본
alter table deals add column readiness_totals jsonb not null default '{}'::jsonb;
--   {"S": {"score": 2.4, "answered": 7, "confidence": 1.0}, ...}  축별 집계
alter table deals add column offering_scores  jsonb not null default '{}'::jsonb;
--   {"01": {"score": 0.72, "rank": 1, "drivers": ["S3","S1"]}, ...}
```

`drivers` 를 같이 저장하는 것이 중요합니다. **"왜 01 이 1등인가" 에 답할 수 없으면 영업이 고객 앞에서 못 씁니다.**

## 7. 변경 계획 — 5단계

기존 동작을 깨지 않는 순서로 잡았습니다. 각 단계가 끝날 때마다 배포 가능합니다.

### STEP 1 · 문항 적재 (엔진 변경 없음)

- `readiness_items` 생성 + 42문항 시드 (AIR-N 원문 + rubric)
- `readiness_fqa_bridge` 시드 — §3 의 ◎5 + ○8 = **13건만**
- 화면 변경 없음. 이 단계만으로는 아무것도 안 바뀝니다

**검증**: 42문항이 축별 7개씩 · bridge 가 가리키는 21문항명이 001 시드와 일치

### STEP 2 · 가중치 행렬 (엔진 변경 없음)

- `readiness_offering_weights` 생성 + 시드
- **`rationale` 없는 행은 넣지 않습니다.** 근거 없는 가중치가 쌓이면 나중에 아무도 못 고칩니다
- 초안은 §2-1 표를 기준으로 하되 **ISSU 검토 필수**

**검증**: 오퍼링 5종이 전부 최소 3문항 이상에서 신호를 받는가 · 어느 문항도 5개 오퍼링을 동시에 부르지 않는가(그러면 변별이 없다)

### STEP 3 · 점수 계산 (읽기 전용 추가)

- `lib/readiness-scoring.js` — 순수 함수. 입력 42응답 + 가중치, 출력 축 점수 + 오퍼링 점수 + drivers
- `POST /api/hub/public/readiness` — 계산만, 저장 없음
- **기존 추천 엔진은 손대지 않습니다**

**검증**: 정규화가 맞는가(문항 수 많은 오퍼링이 항상 이기지 않는가) · 전부 5점이면 모든 오퍼링 점수가 0 인가 · 전부 1점이면 순위가 가중치 분포를 반영하는가

### STEP 4 · 화면 — 42문항 진단

여기서 **응답자 문제를 어떻게 다룰지 정해야 합니다**(§8 결정 ①).

- `/offering` 진단을 42문항으로 교체 또는 별도 경로 신설
- 결과 화면: 6축 레이더 + **오퍼링 순위 + 왜 그런지(drivers)**
- 리포트(PDF·Word·MD)에 오퍼링 순위 포함 — 이미 만들어 둔 `report.js` 를 그대로 씁니다

### STEP 5 · 두 층 연결

- 리드 접수 시 bridge 로 21문항 점수 자동 채움 (13개)
- 허브 STEP02 에 **"42문항에서 자동 채움 13 / 영업 입력 필요 8"** 표시
- 추천 엔진은 그대로 — 입력이 더 채워진 상태로 들어올 뿐

**검증**: 자동 채움 뒤에도 기존 전제조건 판정이 같은 결과를 내는가(회귀)

## 8. 결정이 필요한 것

| # | 항목 | 왜 정해야 하나 |
|:---:|---|---|
| **①** | **42문항을 누가 답하나** | 아래 세 갈래. **이걸 안 정하면 STEP 4 를 시작할 수 없습니다** |
| ② | 21문항을 유지하나 | 버리면 ISV 추천·번들·D-21 로직이 사라집니다(§0). 권고는 유지 |
| ③ | 가중치 초안을 누가 검토하나 | 60~80 셀. 근거 없이 넣으면 추천이 블랙박스가 됩니다 |
| ④ | `/offering` 을 42문항으로 바꾸나 별도 경로를 두나 | 기획안은 42문항을 nimble-dragon(별도 사이트)으로 규정했습니다 |
| ⑤ | D-21 예산 문항을 42 에 더하나 | 없으면 017 의 핵심 변경이 죽습니다. **43번째 문항 추가**가 가장 싼 해법일 수 있습니다 |

### ① 응답자 — 세 갈래

| 안 | 방식 | 장점 | 단점 |
|:---:|---|---|---|
| **가** | **한 사람이 42문항 전부** | 구현이 가장 쉬움 | **20문항이 추측이 됨.** §1 문제의 2배 규모 재현 |
| **나** | **"모르겠음" 허용 + 미응답 처리** | 구현 쉬움, 추측값 안 생김 | IT담당 20문항이 통째로 비면 D·T·G 축이 안 나옴 |
| **다** | **응답자별 링크 분리** (경영진/IT/현업) | 정확함. AIR-N 설계 의도와 맞음 | 초대·취합 기능이 필요. 리드 폼 하나로 안 끝남 |

**권고: 「나」로 시작하고 「다」를 목표로 둡니다.**
「나」는 STEP 4 에서 바로 되고, 축별로 "응답 3/7 — 참고용" 을 표시하면 정직합니다. 「다」는 초대 링크·부분 저장·취합 화면이 필요해 별도 과제입니다.

## 9. 대안 — 20문항 안은 어떻게 되나

진단기준 엑셀의 20문항은 **이미 문항마다 「추천 코어 오퍼링」이 붙어 있습니다.** 가중치를 새로 설계할 필요가 없습니다.

| | 42문항 안 | 20문항 안 |
|---|---|---|
| 가중치 설계 | **새로 만들어야 함** (60~80 셀 + 근거) | **이미 있음** (엑셀 「추천 코어 오퍼링」 열) |
| 응답자 | 4종으로 나뉨 — 운영 방식 결정 필요 | 단일 응답자 전제 |
| 문항 수 | 42 (고객 부담 큼) | 20 |
| 축 정합 | 6축 그대로 | 6영역 그대로 |
| 정밀도 | 축당 7문항 | 축당 3~4문항 |

> **20문항으로 먼저 돌리고 42로 넓히는 길이 있습니다.** 구조(§6 데이터 모델)는 그대로 쓰고 시드만 20 → 42 로 갈아끼우면 됩니다. `readiness_items` 에 문항 수 제약이 없습니다.
> 42 를 바로 하실 거면 §8 ① 을 먼저 정해야 합니다.

## 10. 규모 감

| 단계 | 내용 | 비고 |
|:---:|---|---|
| 1 | 문항·bridge 적재 | 마이그레이션 2개, 테스트 |
| 2 | 가중치 행렬 | **ISSU 검토가 병목** |
| 3 | 점수 계산 + API | 순수 함수라 테스트가 쉬움 |
| 4 | 42문항 진단 화면 | ①에 따라 크게 갈림 |
| 5 | 두 층 연결 + 회귀 | 기존 추천이 안 깨지는지 확인 |

**1~3 은 기존 동작을 전혀 안 건드립니다.** 언제든 멈춰도 손해가 없습니다. 4부터가 화면 변경이고 5가 통합입니다.
