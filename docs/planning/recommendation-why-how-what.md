# 추천 시스템 — Why / How / What

이 문서는 "왜 이걸 만드는가"를 외부에 설명하기 위한 것이다. 설계 세부는 위 두 문서에 있다.

## WHY — 왜 추천 시스템인가

"AI 를 붙이면 좋아 보여서"가 아니다. STEP 03 이 지금 완전 수동이고, 거기서 나오는 문제가 다섯이다.

### 1. 담당자별로 결과가 갈린다
카탈로그 22종(→44종)을 눈으로 훑고 손으로 고른다. 경험 많은 담당자와 신입이 같은 고객에게
다른 조합을 제안한다. 조합이 곧 딜 사이즈라 편차가 매출 편차가 된다.

### 2. "왜 이 조합인가"에 답이 재현되지 않는다
고객 앞에서 근거를 대야 하는데, 근거가 사람 머릿속에 있다. 같은 딜을 다음 주에 다시 보면
설명이 달라진다. **매출로 이어지는 추천이라 설명 가능성이 정확도보다 우선한다.**

### 3. 신규 인력이 못 한다
제안하려면 22종의 특성·전제·궁합을 먼저 익혀야 한다. 온보딩이 곧 카탈로그 암기다.

### 4. 사업 구조상 "조합"이 수익인데 조합을 감에 맡긴다
ISV 라이선스는 재판매 마진이 거의 없다. 수익은 MZC 의 SI·MSP·패키지를 얹은 조합에서 나온다.
딜 사이즈 시뮬레이터가 `multiplier = 총딜 / 라이선스` 를 계산하는 이유다.
그런데 정작 그 조합 구성이 시스템 밖에 있다.

### 5. 이미 쌓이는 데이터를 안 쓴다
대외 랜딩 진단 21문항이 리드마다 들어와 딜에 저장되고, 영업이 STEP 02 에서 취합·수정한다.
**고객의 준비도를 이미 알고 있는데 ISV 선택과 연결되지 않는다.**

## HOW — 어떻게 하는가

### 데이터 흐름

```
대외 랜딩 진단 21문항
      │  POST /api/hub/public/leads  (한 트랜잭션에서 deals + leads 동시 생성)
      ▼
딜 (source=portal, 미배정)  ──claim──▶  STEP 02 에서 영업이 취합·수정
                                              │
ISSU 카탈로그 ─ 판정 데이터 ──────────────────┤
  slot · fqa_coverage · prerequisites          ▼
  red_flags · bundle_potential            추천 엔진 ──▶ STEP 03
  패키지 role · readiness_lift                  │
                                              ▼
                                    추천 vs 채택 기록 ──▶ 기준 튜닝
```

### 설계 결정 6개

**① 평면 순위가 아니라 슬롯 채우기**
22종의 `category` 고유값이 20개다. 서로 비교 가능한 집합이 아니다 — Eleven Labs 와 Zscaler 를
한 줄로 세우는 것은 의미가 없다. "이 슬롯이 이 고객에게 필요한가"를 먼저 판정하고, 순위는
같은 슬롯 안에서만 매긴다. 슬롯 23개 중 경쟁 슬롯은 9개뿐이라 가중치 튜닝이 필요한 범위가 작다.

**② 필터 → 정렬 2단계**
적합도로 후보를 거르고, 남은 후보를 딜 사이즈·번들 확장성으로 정렬한다. 단일 점수에 딜 사이즈를
섞으면 고객에게 불필요한 것이 상위로 올라온다. 영업이 *"귀사 조건에 맞는 건 이 5개이고, 그중
이 조합을 권합니다"* 라고 말할 수 있어야 한다.

**③ 메우는 갭 ≠ 요구하는 갭**
Portal26 은 A(보안)를 메우면서 동시에 A[보안 게이트웨이]를 요구한다. 구분이 없으면
"A 미달 → A 를 메우는 Portal26 추천"이라는 틀린 추천이 나간다. 실제로는 SWG 가 없어 설치 자체가
불가능하다. `fqa_coverage`(메움)와 `prerequisites`(요구)를 분리한 이유다.

**④ 판정 3상태 — 전제 미충족은 탈락이 아니라 번들 기회**
`eligible` / `bundle` / `excluded`. 전제를 못 넘긴 후보를 그냥 떨어뜨리면 준비도가 낮은 고객,
즉 도움이 가장 필요한 고객이 아무것도 못 받는다. 실제 답은 "ISV 전에 MZC 패키지로 준비도를
먼저 올린다"이고 그게 사업 구조와도 맞는다.

**⑤ 패키지와 ISV 는 한 줄로 세우지 않는다**
둘은 다른 질문에 답한다. ISV 는 "무엇을 도입할 것인가", 패키지는 "도입 가능한 상태로 만들려면
무엇을 해야 하는가". 게다가 패키지에는 `synergy`·`grade`·`bundle_potential` 이 없어 가중치
0.45 를 구조적으로 못 받는다. 그래서 패키지에 딜 내 역할(`entry`/`enabler`/`adopt`/`operate`)을
주고 제안을 **준비 → 도입 → 정착·운영** 3단으로 낸다.

**⑥ 결정은 규칙, 문장은 나중에 LLM**
같은 딜에 어제와 오늘 다른 추천이 나오면 영업이 고객 앞에서 신뢰를 잃는다. 추천 순위 결정에
LLM 을 쓰지 않는다. LLM 의 자리는 (a) 콘텐츠 초안 작성 — 오프라인·사람 검토, (b) 3차의 근거
문장 자연어화와 `sections` 인용 Q&A 다. RAG 를 붙여도 인터페이스는 5-STEP 워크플로 그대로다.

## WHAT — 무엇이 나오는가

### 산출물 (구현 완료)

| 산출물 | 내용 |
|---|---|
| **STEP 03 추천** | 준비 / 도입 / 선행필요 / 정착·운영 / 확인필요 / 제외, 각 후보에 근거 문장 |
| **근거 문장** | `준비도 A 1.8/5 — 임계값 3.5 미달, 6/6문항 응답 · "접근권한" 보강` 수준으로 그대로 낭독 가능 |
| **번들 제안** | `INTEGRATION 선행 시 B 2 → 3.5 예상 (전제 3 충족)` — 수치까지 |
| **완성도 게이트** | 발행 전 `{name}` 잔존·템플릿 복붙·슬롯 미배정·커버리지 없음 차단 |
| **피드백 리포트** | 추천 vs 실제 채택. 엔진이 놓친 것 / 판정 데이터 없어 빠진 것 / 추천했는데 안 고른 것 |
| **3단 분류** | 대분류 6 · 슬롯 23 · 개별 솔루션 |

### 기대 효과

| 지표 | 지금 | 목표 |
|---|---|---|
| 조합 구성 근거 | 사람 머릿속 | **문장으로 출력, 재현 가능** |
| 담당자별 편차 | 측정 불가 | 추천 대비 채택률로 측정 |
| 신규 인력 온보딩 | 카탈로그 암기 | 근거 문장이 곧 교육 자료 |
| 패키지 결합 제안 | 감 | 전제 기반 자동 제안 |
| 개선 우선순위 | 감 | **피드백 리포트가 자동 생성** |

### 지금 솔직한 한계

- **후보 풀의 41%만 작동한다.** 22종 중 9종만 판정 데이터가 있다.
- **`security` 대분류 3종(Portal26·Check Point·Zscaler)이 전부 비어 있다.** A(보안)는 가장 흔한
  미달 항목인데 그 영역 ISV 를 하나도 추천할 수 없다. 대신 SECURITY 패키지가 나간다.
- **실단가가 전부 미확정이다.** 딜 사이즈 정렬과 예산 필터가 아직 동작하지 않는다.
- **`readiness_lift` 는 추정치다.** 패키지 산출물과 FQA 문항을 대조해 넣었을 뿐 실사례 근거가 없다.

이 넷은 전부 **데이터 문제이지 엔진 문제가 아니다.** 가중치를 만져도 없는 후보는 나오지 않는다.
그래서 최적화 순서는 콘텐츠 → 측정 → 튜닝이고, 측정 장치(피드백 리포트)를 먼저 깔아뒀다.

### 성공 판단 기준 (3개월)

1. 추천 후보 커버리지 — 22종 중 판정 데이터 보유 **9 → 22**
2. 채택률 — 추천 조합이 실제 `isv_combo` 로 이어진 비율 **측정 시작 → 기준선 확보**
3. "엔진이 놓친 것" 목록 — 매월 줄어드는가 (늘면 판정 데이터가 현실과 계속 어긋난다는 뜻)
