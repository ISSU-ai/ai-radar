# 어디서 막히는가 — 발표 전 정체 지점

> 코드와 실제 API 를 밟아 확인한 것만 적는다. 「그럴 것 같다」는 뺐다.
> 관련: [발표 기획](sales-launch-plan.md)

---

## 한 줄 요약

**발표는 잘돼도 그다음 주에 아무 일도 안 일어날 가능성이 높다.** 이유는 기능이
부족해서가 아니라, 영업이 「해보자」고 마음먹은 뒤 **첫 10분 안에 세 번 막히기**
때문이다.

```
발표 끝 → 써보자 → ① 계정이 없다
                  → ② 딜을 만들면 전부 비어 있다
                  → ③ 42문항이 눈앞에 펼쳐진다
```

---

## 막히는 순서대로

### 🔴 ① 계정을 스스로 만들 수 없다

**확인한 것**: 인증 라우트가 `POST /api/auth/login` · `logout` · `me` **셋뿐이다.**
가입 경로가 없다. 계정은 Supabase 쪽에서 만들어야 하고, 그 뒤 `/admin` 「회원 승인」
에서 `approved` 를 켜야 한다.

**무슨 일이 벌어지나** — 발표장에서 "지금 열어보세요" 하면 **아무도 못 연다.**
채택 곡선이 여기서 0으로 시작한다.

**방향**
- 발표 **전에** 참석자 계정을 전부 만들어 두고 승인까지 켜 둔다
- 발표장에서 나눠줄 수 있게 준비 (초기 비밀번호 · 첫 로그인 안내)
- 명단을 모른다면 최소한 **발표 당일 즉시 만들 사람**을 옆에 세워 둔다

> 이건 제품을 고칠 일이 아니라 **운영 준비**다. 그런데 이걸 안 하면 나머지가 전부 무의미하다.

---

### 🔴 ② 영업이 만든 딜은 아홉 칸이 전부 빈다

**확인한 것**: `POST /deals` 로 딜을 만들고 바로 열어 봤다.

```
42문항 응답    비어 있음
진단 결과      비어 있음
10평가영역     비어 있음
ISV 조합       비어 있음
패키지         비어 있음
배포 인계      비어 있음
고객 원문      비어 있음
담당자         비어 있음
문의 제품      비어 있음
```

**무슨 일이 벌어지나** — 발표에서 본 것(진단 결과가 이미 와 있는 화면)과 **자기가 만든
딜이 완전히 다르다.** "내 건 왜 아무것도 없지?" → 속았다고 느낀다.

**방향 — 발표 대본을 고친다**

데모에서 쓰는 딜은 **포탈로 들어온 딜**이다. 그걸 명시적으로 말한다.

> **"이건 고객이 진단을 답하고 들어온 딜입니다. 여러분이 직접 만드는 딜은
> 비어서 시작합니다 — 그래서 고객에게 진단 링크를 먼저 보내는 게 핵심입니다."**

**그리고 발표의 목표 행동을 바꾼다.** 「딜을 만들어보세요」가 아니라
**「고객에게 진단 링크를 보내보세요」**다. 그게 이 시스템이 실제로 도는 방식이다.

---

### 🔴 ③ STEP02 가 영업에게 42문항을 들이민다

**확인한 것**: `renderFqa()` 의 안내 문구가 *"고객이 포탈에서 답했으면 그 값이 들어와
있고, **아니면 여기서 함께 채웁니다**"* 이고, `renderReadinessQuestions()` 가 6영역
42문항을 전부 그린다.

**무슨 일이 벌어지나** — 빈 딜에서 STEP02 로 넘어가면 **42개짜리 벽**을 만난다.
발표장 실습이 여기서 끝난다.

**방향 (셋 중 택일 — 결정 필요)**

| | |
|---|---|
| **A. 실습에서 STEP02 를 아예 안 간다** | 대본만 고치면 된다. 실습은 `/radar` 검색 5분으로 끝 |
| **B. 빈 딜의 STEP02 를 「진단 링크 보내기」로 먼저 안내** | 42문항을 접는다. 「직접 채우기」는 펼쳐야 나오게 |
| **C. 그대로 둔다** | 실습에서 42문항을 만나는 사람이 나온다 |

**A + B 를 권한다.** A 는 발표 준비, B 는 작은 화면 수정이다.
B 는 「고객이 답하는 게 정상 경로」라는 메시지를 제품이 직접 말하게 만든다.

---

### 🟡 ④ 정체 칩이 남의 딜까지 보인다 — 감시로 읽힌다

**확인한 것**: 딜 카드마다 `stallChipsMarkup(deal)` 이 붙고(`hub.js:249`),
`GET /deals` 에는 담당자 게이트가 없다. **승인된 전 직원이 남의 딜이 빨간지 본다.**

**무슨 일이 벌어지나** — "내 딜이 빨간 걸 다들 보네." 한 번 그렇게 읽히면
되돌리는 데 몇 배가 든다.

**방향** — [발표 기획](sales-launch-plan.md) 의 「발표 전에 정할 것」과 같다.
**본인 딜에만 색을 띄우는 쪽**을 권한다. 신뢰가 쌓인 뒤 열면 된다.

---

### 🟡 ⑤ 포탈 딜은 「담당하기」 전까지 전부 읽기 전용

**확인한 것**: `isOwner()` 가 `owner_id === 내 id` 이거나 admin 일 때만 참이고,
아니면 모든 입력이 `disabled` 다. 포탈로 들어온 딜은 `owner_id` 가 null 이다.

**무슨 일이 벌어지나** — 딜을 열고 뭔가 고치려는데 **전부 회색**이다.
「담당하기」 버튼을 못 찾으면 "고장 났나?"로 끝난다.

**방향** — 규칙 자체는 맞다(남의 딜을 못 고쳐야 한다). **발표에서 한 번 짚고 넘어간다.**
> "포탈로 들어온 딜은 주인이 없습니다. **「담당하기」를 눌러야 내 딜이 됩니다.**"

읽기 전용 상태에 안내 한 줄을 띄우는 것도 방법이다(작은 수정).

---

### 🟡 ⑥ 데모 3에서 빈 절이 나온다

**확인한 것** — 고객용 키트는 재료가 없으면 그 절을 통째로 뺀다.

| 절 | 비면 |
|---|---|
| 비슷한 사례 | **레퍼런스 표가 비어 있어 지금은 항상 안 나온다** |
| 문의하신 제품 | `inquiry_products` 가 비면 절 자체가 없음 |
| 권고 구성 | 「구성을 확정하는 중입니다」 |
| 예상 규모 | 실단가 미확정이라 **금액은 「별도협의」만** |

**방향** — 발표 전에 **데모용 딜 한 벌을 끝까지 채우고**, 레퍼런스를 **최소 3건**
넣는다. 「비슷한 사례」가 있고 없고가 데모 3의 설득력을 가른다.

---

### 🟢 ⑦ 결과 링크를 자동으로 못 보낸다

**확인한 것**: `lib/notify.js` 는 발송 지점만 있고 `MAIL_PROVIDER_URL` 이 없으면
`[mail:skipped]` 로 로그만 남긴다.

**무슨 일이 벌어지나** — 고객이 진단을 마치면 결과 링크가 **화면에만** 뜬다.
영업이 수동으로 전달해야 한다.

**방향** — 발표에서 **약속하지 않는다.** "지금은 링크를 영업이 전달합니다"로 사실대로.
자동 발송은 수단이 정해진 뒤에 말한다.

---

## 그래서 방향

### 발표 대본을 바꾼다 — 가장 큰 것

지금 기획의 목표 행동이 **「`/radar` 북마크」**인데, ②·③을 확인하고 보니
**한 단계 더 앞**이 필요하다.

```
바뀌기 전   /radar 를 북마크한다
바뀐 뒤     담당 고객 한 곳에 진단 링크를 보낸다
```

이유 — 이 시스템은 **고객이 진단을 답하고 들어오는 것**이 정상 경로다. 영업이 빈 딜을
직접 만드는 경로는 부차적인데, 발표에서 그걸 시키면 ②③을 정면으로 만난다.
북마크는 그 앞에 자연히 딸려 온다.

### 발표 전 준비 (없으면 나머지가 무의미)

| | 누가 |
|---|---|
| **참석자 계정 생성 + 승인** | 관리자 |
| 데모용 딜 한 벌 (포탈 유입 · 끝까지 채움) | 준비자 |
| 레퍼런스 3건 | 영업/마케팅 |
| 진단 접수 실적 숫자 | 확인만 |

### 정할 것 둘

1. **정체 칩** — 본인 딜만 색을 띄울 것인가 (④)
2. **빈 딜의 STEP02** — 42문항을 접고 「진단 링크 보내기」를 먼저 보여줄 것인가 (③B)

둘 다 작은 수정이고, 둘 다 **채택 초기의 첫인상**을 바꾼다.
