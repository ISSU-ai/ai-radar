# ISV·패키지 추천 엔진 설계 (2차)

작성 2026-07-27 · 상태: 설계 확정, 구현 전 · 관련 마이그레이션 `010` `011`

## 0. 목적

영업지원시스템의 한 부품. 담당자의 감으로 하던 STEP 03 ISV 조합 구성을, 딜 데이터 기반의
재현 가능한 추천으로 바꾼다. **"왜 이 조합인가"를 고객에게 설명할 수 있어야 한다** — 이게
정확도보다 우선하는 요구다. 매출로 이어지는 추천이라 설명되지 않는 순위는 쓸 수 없다.

기존 planning 문서(`ISSU_허브_개발_프롬프트_AiRadar확장.md` 8-1)의 원칙을 그대로 잇는다.
1단계 = 가중 점수화(속은 규칙, 설명 가능) / 2단계 = 유사 딜 성사율 / 3단계 = pgvector 보조.
이 문서는 1단계다.

## 1. 왜 평면 순위가 아니라 슬롯인가

카탈로그 22종의 `category` 고유값이 20개다. 2종 이상이 공유하는 값은 `GenAI / 범용 LLM`(2)과
`N/A`(2)뿐이다. 즉 `category` 는 분류가 아니라 설명이고, **"이 둘은 같은 자리를 놓고 경쟁한다"를
표현하는 필드가 없다.**

Eleven Labs 와 Zscaler 를 한 줄로 세워 점수를 매기는 것은 의미가 없다. 같은 질문에 답하는
제품이 아니다. 그래서 구조를 이렇게 잡는다.

```
고객 조건(FQA 갭·업종·규모·전제)
        ↓
  ① 어떤 슬롯이 필요한가 판정      ← 추천의 본체. 23개 슬롯 전부에 적용
        ↓
  ② 슬롯 안에서만 후보 경쟁        ← 순위는 여기서만. 경쟁 슬롯 9개
        ↓
  ③ 슬롯 간 조합 + 전제 번들
```

**경쟁 슬롯은 9개, 단독 슬롯은 14개다.** 가중치 튜닝이 실제로 작동하는 곳은 9개뿐이고
나머지는 "필요/불필요" 이진 판정이다. 복잡한 랭킹 모델이 필요 없다.

슬롯은 카탈로그 22종이 아니라 **44종 기준**으로 정의했다. `/radar` 시뮬레이터가 추천하는 36종
중 22종(Databricks·Snowflake·Denodo·ServiceNow·MZC AIR Platform 등)이 아직 카탈로그에 없다.
2차 범위는 22종이지만 슬롯을 22종에만 맞추면 그 22종을 넣는 순간 재작업이 된다.
빈 슬롯은 후보 0으로 남겨둔다. 분류표는 `011` 참조.

## 2. 판정은 3상태다

| 판정 | 조건 | 산출 |
|---|---|---|
| `eligible` | 전제 충족 + 갭 관련 | 단독 추천 |
| `bundle` | 전제 미충족인데 **다른 후보가 그 전제를 메움** | [선행제품 + 본제품] 묶음 |
| `excluded` | 전제 미충족이고 메울 방법 없음, 또는 Red Flag | 제외 + 대안 제시 |

`bundle` 이 핵심이다. 전제 미충족을 그냥 탈락시키면 Portal26 은 SWG 미보유 고객에게 영원히
나오지 않는다. 실제 영업에서 그건 **Zscaler + Portal26 을 함께 파는 기회**다. 끼워팔기가
아니라 기술적으로 필요해서 묶이는 것이라 고객에게 설명도 된다.

## 3. 메우는 갭 vs 요구하는 갭

Portal26 초안에서 드러난 구조다.

```
Portal26
  메움    A[접근권한, 감사로그, 규제대응]  strength 3
          A[데이터 분류]                  strength 2
          C[비용 모니터링]                strength 3
  요구함  A[보안 게이트웨이 준비도] ≥ 3    ← SWG 없으면 설치 자체가 불가
```

**같은 A 카테고리 안에서 메우는 항목과 요구하는 항목이 공존한다.** 카테고리 점수만 보면
"A 미달 → A 를 메우는 Portal26 강력 추천"이 나오는데 이건 틀린 추천이다. A 가 통째로 낮다는
것은 SWG 조차 없다는 뜻이고, 그러면 Portal26 은 얹힐 기반이 없다.

그래서 `fqa_coverage`(메움)와 `prerequisites`(요구)를 분리한다.

### prerequisites 는 2종

```json
[
  { "kind": "fqa", "category": "A", "item": "보안 게이트웨이 준비도", "min": 3,
    "enabled_by": ["zscaler", "check-point"], "blocking": true },
  { "kind": "manual", "label": "프롬프트 보관 노사·법무 검토 완료", "blocking": true }
]
```

| 종류 | 판정 | STEP03 |
|---|---|---|
| `fqa` | 엔진 자동 판정. 실패 시 `enabled_by` 로 번들 생성 | 자동 |
| `manual` | 자동 판정 불가(법무 검토·계약 의사·데이터 보유량) | 확인 체크박스. 미확인 시 "확인 필요" 배지 |

`manual` 확인 결과는 `deals.prereq_confirmations` 에 딜별로 저장한다. 없으면 매번 다시 묻게 된다.

기존 18종 §7.1 이 그대로 들어맞는다.

| 솔루션 | 전제 | kind |
|---|---|---|
| Portal26 | SWG 보유 | `fqa` A:보안 게이트웨이 |
| Articul8 | GPU 서버 인프라 예산 | `fqa` D:예산·구매 준비도 |
| Articul8 | K8s 관리 인프라 엔지니어 | `fqa` C:운영 책임자 |
| Articul8 | 사내 기밀 데이터셋 수만 건 | `manual` |
| LiteLLM | 연동할 LLM API 2개 이상 | `manual` |
| LiteLLM | API 권한 통제 IT 관리자 | `fqa` A:접근권한 |
| Replit | 소스코드 외부 SaaS 저장 법무 허용 | `manual` |

## 4. red_flags 는 대체 추천 그래프

§7.3 에 `➔ 대안` 이 이미 손으로 적혀 있다. 그래프로 만들면 제외가 막다른 길이 아니라
다음 후보로 가는 간선이 된다.

```
Portal26  ──[SWG 없음]───────→ Zscaler / Check Point
          ──[AI 전면차단 폐쇄망]→ Articul8
          ──[대상이 개발 API]──→ LiteLLM
Replit    ──[에어갭 필수]──────→ Articul8
          ──[GPU 직접통제]─────→ Dataiku / DataRobot
Anaconda  ──[거버넌스 니즈 없음]→ Dataiku
          ──[Python 미사용]────→ 도입 비추천
```

## 5. 기준 두 종류

### 기준 A — 슬롯 선정 (23개 슬롯 전부, 여기가 90%)

| 판정 | 근거 |
|---|---|
| 이 슬롯이 메우는 FQA 갭이 미달인가 | `fqa_coverage` × `fqa_totals` |
| 업종이 ○/△/✕ 중 어디인가 | §3.1 → `industries` |
| 규모가 맞는가 | `scale` × `customer_meta.targetUsers` |
| 전제가 충족되는가 | `prerequisites` — 미충족 시 번들 or 제외 |
| Red Flag 에 걸리는가 | `red_flags` → 제외 + 대안 |

필터는 `recommendation_config.kind='filter'` 로 개별 on/off 한다. **값이 없으면 통과**가
원칙이다 — 데이터 미비로 후보가 사라지면 안 된다. 탈락 사유는 전부 기록해 admin 이
"왜 안 나왔나"를 확인할 수 있게 한다.

`budget` 필터는 **기본 OFF**다. 009 시점 모든 단가가 `price_is_placeholder=true` 라 켜면
전 후보가 탈락한다. 실단가 확정 후 켠다.

### 기준 B — 슬롯 내 순위 (경쟁 슬롯 9개에만)

| 항목 | 초기 가중치 | 산식 |
|---|---|---|
| `gap_fit` | 0.40 | Σ(미달폭 × strength) / 정규화 × 신뢰도 |
| `bundle` | 0.25 | `bundle_potential` 1~3 |
| `industry_fit` | 0.15 | high=1.0 / mid=0.5 / 미지정=0.2 |
| `synergy` | 0.10 | 매우높음=1.0 / 높음=0.7 / 중=0.4 |
| `grade` | 0.10 | `grade`/3 |

**신뢰도 보정**: `confidence(cat) = answered(cat) / total_items(cat)` 을 `gap_fit` 에 곱한다.
A 6문항 중 2개만 답한 갭과 6개 다 답한 갭은 신뢰도가 다르다.

`fqa_reviewed_at` 이 없으면 결과에 **"고객 자가응답 기준 잠정"** 라벨을 붙인다. 점수는 깎지
않는다 — 라벨로 충분하고, 깎으면 이중 페널티다.

## 6. 산출 UI (STEP 03)

```
■ 바로 도입 가능              ← eligible, 딜사이즈 정렬
■ 선행 조건이 필요            ← bundle, 딜사이즈 정렬
■ 확인 필요                   ← manual 전제 미확인
■ 제외됨                      ← 사유 + 대안, 접어두기
```

`eligible` 과 `bundle` 을 한 줄로 세우면 번들이 항상 위로 간다(제품 2개니까). 영업이 고객
앞에서 "지금 되는 것"과 "선행이 필요한 것"은 다른 대화다. 그룹을 나눠야 그 대화가 된다.

수동 선택은 그대로 유지한다. 추천은 제안이지 강제가 아니다.

## 7. 근거 문장 (LLM 불필요)

점수 계산 시 항목별 사유를 문자열로 남긴다.

```
Zscaler + Portal26   (번들)
 · 준비도 A(보안·거버넌스) 1.8/5 — 임계값 3.0 미달, 6문항 전부 응답
 · Portal26이 "접근권한·계정 체계" "감사 로그와 추적성" "규제·컴플라이언스"를 직접 보강
 · 단, Portal26은 SWG를 전제로 하며 현재 미보유 → Zscaler 선행 필요
 · Zscaler 구축 후 Portal26 연동은 ZIA·DLP·ZIR 구성만으로 완료
 · 업종 금융/보험 적합(high)
```

영업이 이 문장을 그대로 고객에게 읽을 수 있어야 한다. STEP05 세일즈 피치가 이미 같은
방식으로 `failing` 카테고리를 문장에 넣고 있어 패턴이 검증돼 있다.

## 8. 입력 데이터

FQA 21문항은 대외 랜딩 자가진단에서 먼저 들어온다. `POST /api/hub/public/leads` 가 한
트랜잭션에서 `deals`(source='portal', owner_id=NULL)와 `leads`(promoted_deal)를 동시 생성하므로
**승격 단계가 따로 없다.** 영업은 claim 만 하면 되고, STEP02 에서 취합·수정한다.

| 입력 | 출처 | 상태 |
|---|---|---|
| FQA 점수 | 랜딩 → `deals.fqa_scores` → STEP02 수정 | 있음 |
| 카테고리 가중점수·임계값 | `fqa_totals`, `fqa_items.weight/threshold` | 있음 |
| 갭 판정 신뢰도 | `fqa_totals[cat].answered` | 있음 |
| 업종·규모·보안스택·투자여력 | `customer_meta` | 있음 |
| 트랙 | `deals.track` | 있음 |
| 검토 여부 | `deals.fqa_reviewed_at` | **010 신규** |
| 자가응답 원본(편차 분석) | `leads.fqa_scores` | 있음 (3차용) |

## 10. 3차 확장 지점

| 확장 | 조건 |
|---|---|
| 근거 문장 자연어화 | 규칙 엔진이 먼저 있어야 설명할 대상이 생긴다 |
| `sections` 인용 Q&A 보조 패널 | `solution_chunks` 인덱싱 시 **`visibility` 컬럼 필수**. 현재 RLS 가 `is_approved()` 라 승인 전 직원이 전 청크를 읽는다. 인덱서는 `lib/section-privacy.js` 를 통과시켜 `sections_internal`·`opinion`·가격을 넣지 않는다 |
| 유사 딜 성사율 | `recommendation_snapshot` 과 실제 `isv_combo` 대조. 모수가 쌓여야 한다 |
| `bundle_potential` 자동화 | 성사 딜의 `multiplier` 실적으로 admin 수동 입력을 대체 |

**LLM 은 추천 결정에 관여하지 않는다.** 결정은 규칙이, 문장은 LLM 이. 같은 딜에 어제와
오늘 다른 추천이 나오면 영업이 고객 앞에서 신뢰를 잃는다.

RAG 를 붙여도 인터페이스는 5-STEP 워크플로 그대로다. 채팅으로 바꿀 이유가 없다 — 이미
구조화된 입력(FQA 21점수·업종·규모·예산)을 폼으로 정확히 받고 있고, 딜은 상태를 가진
레코드이며, 산출물은 재현 가능해야 한다.
