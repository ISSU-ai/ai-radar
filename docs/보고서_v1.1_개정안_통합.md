## 0. 개정 배경 — 무엇이 문제였는가

v1.0 검토 과정에서 아래 3가지가 확인되었다.

| 1 | **인원 배분이 역산값이다** | 6.2 이동 매트릭스의 인원(유휴 ~50, Max 5x 60/44, Premium 15/70/58 등)은 시트 150+150이 맞아떨어지도록 배치한 값으로, 실측 근거가 없다. 특히 유휴 ~50은 4.2 예산 계산이 성립하도록 역산한 편의값이다 |

## 2. 신설 — 3.4 배분 산출 시트

> **삽입 위치**: 3장, 기존 3.3(초과분 전환 시나리오) 뒤
> **설계 원칙 2가지**
> 1. **총무팀이 보유한 데이터만 요구한다** — 계정 목록, 최근 활동일, 플랜명, 계정 식별자. 토큰 소비량은 Team 플랜 특성상 총무팀이 확인할 수 없으므로 요구하지 않는다.
> 2. **판단을 요구하지 않는다** — "이 사람이 헤비인가"를 묻지 않고, 세거나 옮겨 적기만 하면 되도록 구성한다.


### 3.4.1 산출 순서

배분은 아래 3단계로 산출한다. STEP 1·2는 총무/IT지원팀이 작성하고, STEP 3은 자동 계산된다.

```
STEP 1    계정 현황 집계     (총무/IT지원팀 · 콘솔 export)
STEP 1-B  도구 중복 집계     (총무/IT지원팀 · 사번 기준 대사)
STEP 2    유형 분류 집계     (부문별 설문 회수 후 집계)
STEP 3    배분 자동 산출     (STEP 1·1-B·2 값 대입)
```

---

### STEP 1. 계정 현황 집계표

**작성 방법**: 벤더 Admin 콘솔에서 사용자 목록을 내려받아 최근 활동일 기준으로 개수만 센다.

| 구분 | 현재 계정수 | ① 90일 무활동 | ② 30~89일 무활동 | ③ 활성(30일 내) | 검산 |
|---|---|---|---|---|---|
| Claude Max 20x | 9 | | | | ①+②+③ = 9 |
| Claude Max 5x | 104 | | | | ①+②+③ = 104 |
| Claude Premium | 143 | | | | ①+②+③ = 143 |
| Claude Std | 101 | | | | ①+②+③ = 101 |
| **Claude 소계** | **357** | **= A** | **= B** | **= C** | A+B+C = 357 |
| ChatGPT | 66 | | | | |
| Cursor | 88 | | | | |
| GitHub Copilot | 27 | | | | |

**용어 정의**
- 최근 활동일 = 콘솔의 Last active / Last seen 항목
- 90일 무활동(A) = 즉시 회수 대상 (유휴 계정)
- 30~89일 무활동(B) = 관찰 대상 (회수 보류, 재판정 시 판단)

---

### STEP 1-B. 코딩 도구 중복 집계표

현황표상 557 라이선스 대비 사용자 411명(1인당 1.36개)으로, 다수 계정을 보유한 사용자가 존재한다. 중복의 상당 부분은 코딩 보조 도구로 추정되나 현재 확인된 바 없다. Claude·Cursor·Copilot은 별개 모집단이 아니라 겹치는 집합이므로, 아래 교차 집계 없이는 STEP 3 배분과 5.1 Cursor 판정 모두 근거를 갖지 못한다.

**작성 방법**: 3개 도구의 콘솔 export를 사번(또는 사내 이메일) 기준으로 대사하여 조합별 인원을 센다.

| 보유 조합 | 인원 | 판정 |
|---|---|---|
| Claude 단독 | | 중복 없음 — 그대로 |
| Claude + Cursor | **= I** | 정리 후보 1순위 |
| Claude + Copilot | **= J** | 정리 후보 |
| Claude + Cursor + Copilot | **= K** | 즉시 정리 대상 (3중 보유) |
| Cursor 또는 Copilot 단독 (Claude 미보유) | **= L** | 별도 판단 — Claude 배분 대상 아님 |

**검산**

```
I + J + K + (Cursor·Copilot 단독 L) ≤ 88 + 27 = 115
```

> K(3중 보유)는 기능이 중복되는 도구를 동시에 세 개 보유한 조합으로, 업무상 필요로 설명되기 어렵다. K는 STEP 3 배분과 무관하게 즉시 정리 대상으로 분류한다.

### STEP 2. 유형 분류 집계표

**작성 방법**: 전 대상자에게 아래 3문항 설문을 발송하고, 부문별 응답 수를 집계한다. 미응답자는 현행 플랜 기준으로 자동 분류한다(3.4.3 참조).

**설문 문항 (3문항, 객관식)**

1. Claude를 주로 어떤 방식으로 사용하십니까?
   - (1) 웹 화면(claude.ai)에서 대화
   - (2) Claude Code 등 터미널·개발도구
   - (3) 우리 팀 제품·시스템에 API로 연결
   - (4) 거의 사용하지 않음

2. 하루 평균 사용 빈도는?
   - (1) 하루 10회 이상 · (2) 하루 3~9회 · (3) 주 3회 이하 · (4) 거의 없음

3. 소속 부문: __________

**집계표**

| 유형 | 판정 기준 (문1·문2) | 인원 |
|---|---|---|
| **T1 코드 에이전트형** | 문1 = (2) | = D |
| **T2 임베디드형** | 문1 = (3) | = E |
| **T3 대화형 고빈도** | 문1 = (1) AND 문2 = (1)·(2) | = F |
| **T4 대화형 저빈도** | 문1 = (1) AND 문2 = (3)·(4) | = G |
| **T5 미사용** | 문1 = (4) OR 문2 = (4) | = H |
| **합계** | | D+E+F+G+H = C (활성 계정수) |

---

### STEP 3. 배분 자동 산출

STEP 1·2에서 확정된 A~H를 아래 식에 대입한다.

**계산식**

| 항목 | 계산식 | 산출 근거 |
|---|---|---|
| 회수 대상 | **A** | 90일 무활동 = 즉시 회수 |
| Bedrock API (직결) | **D + E** | 코드 에이전트·임베디드는 UI 불필요, Bedrock 직결로 무마찰 전환 |
| ChatGPT Ent 시트 (Claude에서 이동) | **min(F, 84)** | 대화형 고빈도는 정액이 유리. ChatGPT 여유석 84 한도 |
| Claude Ent 시트 | **min(G + H, 150)** | 저빈도·저사용자 우선 배정 (파트너십 활성 요건 충족용) |
| Bedrock API (추가) | **(F − 84 초과분) + (G + H − 150 초과분)** | 시트 부족분은 API + 그룹 풀로 흡수 |
| 관찰 유예 | **B** | 30~89일 무활동, 분기 재판정까지 현 상태 유지 |
| 코딩 도구 정리 | **K** (즉시) + **I** (관찰 후) | Bedrock 직결 배정자(T1)가 Cursor·Copilot을 중복 보유한 경우, 배분과 별개로 도구 라이선스를 정리한다 |

**검산식**

```
A + D + E + min(F,84) + min(G+H,150) + 초과분 + B = 357
```

**시트 요건 검산**

```
ChatGPT Ent 총계 = 66(기존 승계) + min(F,84)  →  150 이하여야 함
Claude Ent 총계  = min(G+H,150)              →  100 이상이어야 함 (파트너십 활성 요건)
```

> Claude Ent가 100 미만으로 산출될 경우, T3(대화형 고빈도) 중 사용 빈도 하위자를 Claude Ent로 재배정하여 요건을 충족시킨다.

STEP 3 결과를 아래에 대입하여 연간 비용을 산출한다.

| 항목 | 계산식 | 비고 |

## 3. 대체 — 5.1 코딩 보조 도구 스택 정리

> **대체 대상**: 기존 5.1 "Cursor 88계정 — 조건부 정리" 전체
> **재작성 사유**: 실제 문제는 Cursor 단품이 아니라 코딩 보조 도구에 표준이 정의된 바 없다는 것이다. 개별 도구의 정리 여부만 판정하면 표준 부재라는 원인이 남아 동일 문제가 재발한다. ChatGPT Enterprise 전환 시 Codex가 추가되어 도구가 4개로 늘어나므로 판정 시점을 전환 이전으로 앞당긴다.


### 5.1.1 현황 — 4개 도구 병존

| 도구 | 계정 | 연비용(USD) | 조달 형태 | 비고 |
|---|---|---|---|---|
| Cursor | 88 | 33,792 | 개별 구독 | $32/석 |
| GitHub Copilot | 27 | 6,156 | 개별 구독 | $19/석 |
| Claude Code | — | Claude 라이선스에 포함 | 시트 내장 | 별도 과금 없음(현행 정액) |
| Codex | — | ChatGPT Ent 시트에 포함 | **전환 후 신규** | 크레딧 소비 방식 |

현행 직접 지출은 Cursor·Copilot 합산 **연 39,948달러**(전체 예산의 9.9%)다. 여기에 Claude Code가 이미 내장되어 있고, ChatGPT Enterprise 전환 시 Codex가 추가되어 **1인이 최대 4개 도구를 보유하는 구조**가 된다.

현황표상 557 라이선스 대비 사용자 411명(1인당 1.36개)이나, 중복의 구성은 확인된 바 없다. 정리 대상 산출은 STEP 1-B 대사 결과를 전제로 한다.

### 5.1.2 계층 분석 — 대체 관계와 보완 관계의 구분

정리 판단의 전제는 "중복"이 아니라 "대체 가능성"이다. 요청서가 제시한 "Claude Code와 중복"이라는 근거는 계층을 구분하지 않은 것으로, 그대로 적용할 경우 방어가 어렵다.

| 계층 | 도구 | 작업 방식 |
|---|---|---|
| **A. IDE 보조** | Cursor, GitHub Copilot | 편집기 내 자동완성·인라인 편집. 개발자가 코드를 직접 작성하며 보조받는 형태 |
| **B. 터미널 에이전트** | Claude Code, Codex | 작업을 위임하고 결과를 검토하는 형태. 파일 생성·수정·실행을 에이전트가 수행 |

**판정**

| 조합 | 관계 | 판단 |
|---|---|---|
| Cursor + Copilot | **대체 (동일 계층)** | Cursor가 Copilot 기능을 포괄한다. 동시 보유는 명백한 중복 |
| Cursor + Claude Code | **보완 (계층 상이)** | 병용이 자연스럽다. 중복을 근거로 한 정리는 성립하지 않음 |
| Claude Code + Codex | **대체 (동일 계층)** | 전환 후 발생. 표준 선택 필요 |
| Cursor + Copilot + Claude Code | 대체 1건 포함 | Copilot이 잉여 |

> 코드 유출 리스크에 관하여: Cursor의 기본 설정에서 코드 스니펫이 외부로 전송될 수 있다는 지적은 사실이나, 이는 Privacy Mode 정책 강제로 해소 가능한 설정 항목이다. 따라서 폐지의 근거로는 불충분하며, 도구 유지 여부와 무관하게 **정책 강제 항목**으로 별도 관리한다(7.1 연계).

### 5.1.3 표준 스택 권고

```
개발자 1인 표준 = 터미널 에이전트 1개 + IDE 보조 1개

  터미널 에이전트 : Claude Code 또는 Codex 중 택1  (→ 5.1.5 결정 요청)
  IDE 보조        : Cursor 또는 Copilot 중 택1
                    - 상시 사용자    → Cursor ($32)
                    - 간헐 사용자    → Copilot ($19)
                    - 미사용         → 미배정
```

**원칙 3가지**

1. **동일 계층 2개 보유는 불허한다.** 표준 이탈은 부문장 승인과 사유 기록을 요한다.
2. **IDE 보조는 단가 차등을 적용한다.** Cursor와 Copilot의 단가 차이(월 $13)는 사용 강도에 따라 배정 근거가 된다.
3. **도구 배정은 시트/API 배분과 독립적으로 관리한다.** Bedrock API 배정자(T1)도 IDE 보조는 별도로 필요하며, 반대로 시트 보유자가 코딩 도구를 요하지 않을 수 있다.

### 5.1.4 정리 대상 산출

STEP 1-B(3.4) 대사 결과를 아래에 대입한다.

| 구분 | 산출식 | 조치 | 회수액(연) |
|---|---|---|---|

## 4. 신설 — 7.3 크레딧 운영 체계

> **삽입 위치**: 7장, 기존 7.2(토큰 효율화 4대 레버) 뒤
> **작성 사유**: 6.7 R&R이 전환 기간(W0~W4) 한정이어서 프로젝트 종료 후 운영 주체가 공백 상태다.


배분 규칙(7.1)이 정의되어도 이를 매월 집행할 주체와 절차가 없으면 규칙은 작동하지 않는다. 본 절은 전환 완료 이후의 상시 운영 체계를 정의하며, 프로젝트 종료 시 귀사 운영 조직으로 이관되는 범위에 해당한다.

### 7.3.1 역할 3분리

크레딧 배분에서 집행·판정·승인을 한 조직이 겸하면 운영이 지속되지 않는다. 운영팀이 증액 여부까지 판정할 경우 매월 전 부문과 이해 조정을 수행해야 하며, 이는 실무적으로 유지 불가능하다. 따라서 아래와 같이 분리한다.

| 기능 | 주체 | 책임 범위 |
|---|---|---|
| **집행** | AI 운영팀 (어드민) | 풀 배포, 소진 모니터링, 증액 반영, 대시보드 운영, 이상 소비 탐지·통보 |
| **판정** | 부문장 | 소속 부문의 증액 필요성 판단, 산출 연계 확인, 개인 단위 증액 신청 대리 |
| **승인** | 재무 + AI 총괄 | 예비 풀 집행 승인, 분기 재판정 결과 확정, 기본치 조정 승인 |

> 운영팀은 판정하지 않는다. 운영팀의 산출물은 "누가 얼마를 썼는가"이며, "더 줄 것인가"는 부문장의 판단과 승인 라인의 결정 사항이다.

### 7.3.2 월간 운영 캘린더

| 시점 | 작업 | 주체 |
|---|---|---|
| 월 1영업일 | 부문 풀 배포 (확정 기본치 기준), 배포 내역 부문 통보 | 운영팀 |
| 월 10일 | 1차 소진 점검 — 이상 소비 패턴 부문 통보 | 운영팀 |
| 월 15일 | 중간 증액 접수 마감 (소진률 90% 초과 부문 대상) | 부문장 → 운영팀 |
| 월 18일 | 중간 증액 집행 (성과 예비에서, 기본치의 20% 이내) | 승인 라인 |
| 월 말일 | 실소진 집계, 익월 기본치 산출(직전 실소진 × 1.2 상한) | 운영팀 |
| 익월 3영업일 | 익월 기본치 확정 통보 | 승인 라인 |
| 분기 말 | 재판정 — 미소진 부문 기본치 하향, 예비 환수, 시트↔API 교차 이동 | 승인 라인 |

### 7.3.3 증액 처리 기준

**지급 조건 (동시 충족)**
1. 부문 풀 소진률 80% 이상
2. 부문장의 산출 연계 확인 — 소진이 업무 산출과 연결됨을 확인

소진률만으로는 지급하지 않는다. 반복 프롬프트 등 비효율 소비가 증액으로 보상되는 구조를 차단하기 위함이다.

**거절 사유 3분류** — 회신은 아래 세 가지로 정형화하여 운영 부하를 통제한다.

| 사유 | 판정 근거 | 후속 조치 |
|---|---|---|
| A. 소진률 미달 | 소진률 80% 미만 | 현 배정 유지, 익월 재신청 안내 |
| B. 산출 미확인 | 소진 대비 산출 연계 불명확 | 유저별 드릴다운 후 교육 트랙 배정 |
| C. 라우팅 점검 필요 | 단순 작업의 최상위 모델 사용 비중 과다 | 모델 라우팅 정책 점검 후 재심 |

### 7.3.4 이관 요건

프로젝트 종료 시 아래를 충족한 상태로 운영 조직에 이관한다.

- 운영자 2명 이상 지정 (1인 운영 시 부재 리스크 — 백업 필수)
- AIR Studio 어드민 권한 및 대시보드 접근 확보
- 월간 캘린더 1회 이상 동행 수행 (인수인계 실주행)
- 증액 신청·거절 템플릿 및 판정 기준 문서 이관
- 이슈 로그(8.1) 이관 — 계열사 확대 적용 시 참조

## 5. 보강 — 7.1 단계 배포 상세

> v1.0에 원칙(60/30/10, 계수 0.8)은 반영되었으나, 산정식과 운영 사이클 상세는 미반영 상태다. 아래를 7.1 하단에 보강한다.

### 7.1-a 풀 분할 구조

```
연간 API 풀 (S-B 기준 225K, S-0 성립 시 300K)
├─ ① 기본 배포   60%   부문 그룹 풀 — 균등 아닌 인원×기본 소비량 기준
├─ ② 성과 예비   30%   소진 실적 기반 부문 증액 재원 (M+1부터 개방)
└─ ③ 전략 예비   10%   신규 프로젝트 · 9/1 단가 인상 버퍼 · 총괄 승인제
```

- 배포 단위는 **부문 그룹 풀**. 개인 배정은 이전·이월 불가로 미사용분이 소멸하므로 원칙적으로 금지, 이상 소비자 하드캡만 예외.
- ②·③은 AIR Studio 상 미배정 상태로 보관. 존재 자체를 공지하되 자동 지급되지 않음을 명시.

### 7.1-b 기본 소비량 산정 (M0 — 실측 이전)

실측이 없으므로 벤더 참고치 × 부문 인원으로 초기값을 만든다.

| 사용자 유형 | 월 기본치 (크레딧) | 근거 |
|---|---|---|
| 개발 (에이전트 사용) | 5,000 | 벤더 가이드: 개발자 5,000 ≈ Pro급 |
| 일반 (대화형) | 500 | 벤더 가이드: 일반 500 시작 |
| 간헐 | 200 | 자체 보수 추정 |

```
부문 기본 풀 = Σ(유형별 인원 × 기본치) × 0.8
```

× 0.8은 의도적 과소 배포 계수 — 부족은 증액으로 풀 수 있지만 과잉은 소멸로 끝난다.

### 7.1-c 운영 사이클

| 시점 | 작업 | 판단 주체 |
|---|---|---|
| M0 (배포) | 부문 기본 풀 배포, 소진 대시보드 개통 | 컨설팅 PM |
| M0+2주 | 중간 점검 — 소진률 90% 초과 부문은 예외 선증액 (②에서, 상한 20%) | PM 전결 |
| **M1 (4주)** | **부문별 소진 실적 확정 → 소비 지형 판독 → 증액 체계 수립** | PM + 부문장 |
| M1 이후 | 월간 증액 사이클 상시화 | 아래 4항 규칙 |
| 분기 | 재판정 — 미소진 부문 기본치 하향, 예비 환수 | PM + 재무 |

**M1이 분기점이다.** 이전까지는 규칙이 아니라 임시 전결로 운영하고, 4주 데이터가 쌓인 뒤에야 증액 기준을 명문화한다. 데이터 없이 만든 규칙은 첫 달에 예외투성이가 된다.

### 7.1-d 증액 규칙 (M1부터 적용)

부문 단위 신청·부문 단위 지급. 개인 증액은 부문장 경유로만.

**지급 조건 (둘 다 충족):**
1. 부문 풀 소진률 ≥ 80%
2. 산출 확인 — 소진이 업무 산출과 연결됨을 부문장이 확인 (반복 프롬프트형 낭비 소진은 증액이 아니라 교육 트랙 대상)

**지급량:** 직전 월 실소진 × 1.2 를 신규 기본치로 갱신 (일회성 충전이 아니라 기준선 이동)

**거절 시:** 사유 회신 + 교육 트랙 또는 모델 라우팅 점검 안내

### 7.1-e 소비 지형 판독 기준 (M1 판단용)

| 패턴 | 해석 | 조치 |
|---|---|---|
| 소진 ≥ 90% + 산출 확인 | 진성 고소비 부문 | 기본치 상향 (②에서) |
| 소진 ≥ 90% + 산출 불명 | 낭비 의심 | 유저별 드릴다운 → 교육/라우팅 |
| 소진 40~80% | 적정 | 유지 |
| 소진 < 40% | 과대 배정 | 분기 재판정 시 기본치 하향, 차액 ② 환수 |
